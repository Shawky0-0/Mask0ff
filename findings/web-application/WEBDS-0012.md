## What happens

Laravel can hand out a link to a private file that works for a limited time. It
builds the link, then signs it, so the server can later check that nobody edited
it. The signature covers the whole query string, expiry included.

The bug is that the file path went into that query string raw. If the filename
contains a question mark, the question mark stays a question mark. A URL does
not treat that as part of the filename, it treats it as the start of a new query
section.

## Why it works

Two readers, one string, two readings. The signer thinks the path is
`report.pdf?pad=x`. The server splits at the question mark and reads the path as
`report.pdf`, with `pad=x` as a separate parameter. Because the pieces the
server ends up with are not the pieces the signer signed, the expiry check can
end up applied to a value that is no longer where the server is looking. The
practical outcome the advisory names is that expiry stops being enforced, and
that requests can land on a resource nobody meant to expose. On the upload
variant the same confusion can send a write somewhere unintended.

Note the severity is moderate and privileges required is low, not none. You need
to be able to get a signed URL in the first place, and you need influence over
the filename. This is not a pre auth bug.

## How you would reproduce it

Stand up a Laravel app below the fixed version. Put a file in local storage with
a question mark in the name and a known marker inside it. Generate a temporary
URL with a five second expiry. Wait ten seconds. Request it. If the marker comes
back, the expiry was not enforced. Then repeat with a plain filename and confirm
you get rejected. That second run is the control that makes the first one mean
something.

## What the fix is, and why the obvious fix would not work

The fix is `rawurlencode()` on the path before it becomes a route parameter.

The obvious fix would be to strip or reject question marks in filenames. That
fails for two reasons. First it is a denial list, and denial lists on URI
grammar are famously incomplete: you would also need `&`, `#`, `%`, `/`, `+`,
and whatever the next parser disagrees about. Second it fixes the symptom in one
driver while leaving the actual rule unstated. Encoding at the boundary states
the rule once and covers every character at the same time.

A second thing worth noticing: the fix needed three pull requests, not one.
60137 encoded the path, and 60230 and 60350 followed. A single line change that
takes three attempts usually means the first attempt broke something that
depended on the old behaviour, which is normal for encoding fixes and is why
they get deferred so often.

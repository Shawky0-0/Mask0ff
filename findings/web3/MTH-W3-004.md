# MTH-W3-004: follow every signature back to the moment of consent

**YZH runs no web3.** This card is filed here because web3 made the pattern
visible, but it is a general authorisation method. Related:
W3DS-0011,
MTH-W3-005,
MTH-W3-001.

## The technique in one line

For every signature, token or approval a system accepts, ask three questions: when
was it created, what could the person creating it actually see, and what stops it
being spent somewhere else later.

## The discovery signal

Words in the design that separate approval from execution. **Durable. Offline.
Queued. Pending approval. Pre approved. Sign now, submit later. Scheduled.**
Anywhere a human says yes at one moment and the effect lands at another, there is a
gap, and the gap is where this lives.

The second signal is a confirmation screen that summarises rather than shows. If the
approver sees "Approve deployment 4471" and not the change, their consent is
attached to something they never read.

## The mechanism

An authorisation is really three facts bundled together: **who agreed**, **to what**,
and **when**. Cryptography protects the first one very well and says nothing about
the other two unless somebody deliberately binds them.

So the failure comes in two flavours and they compose.

**Time.** If nothing expires the authorisation, it stays spendable. Drift's Security
Council signed transactions using Solana durable nonces, which exist specifically to
remove the normal staleness limit. The signatures sat dormant and were submitted on
2026-04-01, valid, transferring admin control. Nothing was forged.

**Intent.** If the signer cannot read what they are signing, they agreed to whatever
the bytes say. The council members were told they were approving something routine.

Together they are worse than either alone. The attacker gets consent under one
understanding and spends it later under another, and every signature check along the
way returns true.

## Which of the six areas

**Wallets and signing**, primarily. It touches **the seam** wherever a web front end
constructs what the user will sign.

## Does this reach a normal web application, and how

**Yes. This is the strongest transfer in the folder so far, and none of it needs a
chain.** The same shape, in things Ahmed already tests:

* A password reset link with no expiry, or one that survives being used.
* A signed URL, for a download or an upload, whose lifetime nobody set.
* An API token issued for one purpose that carries the user's full rights.
* A CRM or CI approval step where the approver sees a title rather than a diff.
* An OAuth consent screen that says "access your account" and grants more.
* Any webhook or callback that is accepted without checking how old it is.

For the education app fleet the concrete version is: find every artefact the system
issues that grants something later, and for each one write down its expiry and what
the person who authorised it saw. **The ones with no expiry and no visible intent
are the finding**, and you can build that list by reading, with no target touched.

## A safe way to look for it

1. List every place the system accepts proof of a past decision: signatures, tokens,
   links, approval records, signed cookies.
2. For each, find where it is created and where it is spent. If they are in the same
   request, move on. If they are not, keep going.
3. Write down the lifetime. If you cannot find one in the code, there is not one.
4. Write down what the authoriser saw at creation time. Get the actual screen or the
   actual template, not a description of it.
5. Ask what changes between creation and spending. Roles, prices, permissions,
   configuration. Anything that can change is something the consent did not cover.

No exploitation is required to produce that table, and the table is the deliverable.

## The control that catches a false positive

The shape is **not** present when both hold: the authorisation carries an expiry the
server enforces, **and** it commits to a specific payload the authoriser saw, for
example a hash of the exact change. Check that the expiry is enforced rather than
merely stored. A field called `expires_at` that nothing compares against is
decoration.

Second false positive: a delayed approval inside one trust boundary, where the same
party creates and spends it and nobody else can reach it. Lower value, say so and
move on rather than padding the report.

## Where else this shape appears

Offline signing of any kind. Deploy and release approvals. Purchase orders. Pre
authorised card payments. Bank standing instructions. Consent forms signed in
advance of a procedure. The pattern is older than software, and software mostly
removed the expiry that the paper versions had.

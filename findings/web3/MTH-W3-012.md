# MTH-W3-012: ask what the client remembered, and who is allowed to change it

**YZH runs no web3. This card is not a finding about the fleet.** Related:
W3DS-0023,
MTH-W3-009,
W3DS-0030.

## The technique in one line

Find every value the client read once and kept, then ask who else can change that
value, and what happens between the change and the client noticing.

## The discovery signal

A variable set during setup and used for the rest of the session, especially one
used to build an address, a URL, a route, a price or a permission. In the source
finding it was the chain identifier, captured at connection time and then used to
work out which contract to send money to.

## The mechanism

Two systems hold a copy of the same fact. Only one of them owns it.

The client caches the fact because asking every time is slow, and because at the
moment it asked, the answer was correct. The owner changes the fact whenever it
likes, because it is the owner. Between those two moments the client is confidently
wrong, and confidence is the problem: it does not fail, it acts.

The dangerous version is when the cached value is used to derive something rather
than merely displayed. A stale value shown on screen is a cosmetic bug. A stale
value used to compute where money goes is the finding.

Note the specific gap in the source case: the value went stale **during the
connection flow itself**, before the application was listening for change events.
Subscribing to changes does not cover the window before you subscribed.

## Which of the six areas

The seam. This is the dApp front end's own runtime boundary with the chain, which
is the highest weighted row in this folder.

## Does this reach a normal web application

**Yes, directly, and nothing in it is web3 specific.** The wallet is only an
unusually visible example of an authority the user can change behind the
application's back. On an ordinary web application the same shape is:

* The tenant, workspace or organisation captured at login, while the user switches
  organisation in a second tab.
* The role or permission set loaded once into front end state, after an
  administrator changes it.
* The currency, tax region or locale captured at session start and used to compute a
  price.
* A feature flag read at boot and used for the life of a long running worker.
* The account balance or stock level read on page load and used to decide what to
  submit.

## A safe way to look for it

Read only, and it works on any application Ahmed is authorised to test.

1. List the values the client holds in its own state after startup.
2. For each, mark whether it can change without the client acting: yes or no.
3. For every yes, ask what the client uses it for. Displayed only, or used to derive
   an address, a route, a permission, a price.
4. The derived ones are the hypotheses.
5. Test them by changing the value in the second place, out of band, then acting in
   the first place without reloading.

The two place test is the key move, and it is the same discipline as
MTH-W3-009: a bug about two states
is invisible when you only ever hold one.

## The control that catches a false positive

**A re render is not a re read.** A component that updates on screen may still be
reading the same stale variable, so watching the interface change proves nothing.
Check what the action actually sends, not what the page shows.

Second control: confirm the value is genuinely used to derive something. Plenty of
cached values are cosmetic, and reporting those as security findings burns
credibility.

Third: check whether a change event exists and is subscribed to **before** the
window in which the value can first change. In the source case it was not, which is
why the event based fix alone would have missed it.

## Where else this shape appears

Any long lived client: a single page application, a mobile app, a background worker,
a queue consumer, a cached API gateway. Also configuration read at process start in
a service that runs for weeks.

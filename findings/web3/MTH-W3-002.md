# MTH-W3-002: Read the dependency's publish pipeline, not only its code

Related: W3DS-0003,
W3DS-0010,
W3DS-0008.

## The technique in one line

For any dependency, stop asking whether the code is good and ask what it would take for a stranger to
publish code into your build.

## The discovery signal

Public registry and repository metadata answers all of it, and none of it requires installing anything:

* A version published minutes after a commit, which means no human stood between them.
* A monorepo where one version bump publishes many packages at once.
* Commits landing directly on the default branch with no pull request.
* Any `postinstall` or `preinstall` script.
* A `repository` field that points nowhere, or nowhere related to the brand in the name.
* A burst of several packages published by one account within a couple of minutes.

## The mechanism

A dependency is not a snapshot of code, it is a standing permission for whoever controls the publish
path to run code on every machine that installs it. So the trust question is about the path, not the
snapshot.

Two incidents this run show both ends of that path:

* **Injective, 2026-07-08.** One compromised maintainer account, direct push to master, CI publishing on
  version bump, and a monorepo release train. Result: 18 backdoored packages live in about five minutes,
  with a hook inside `PrivateKey.fromMnemonic()`. Reading the repository the day before or the day after
  shows clean code, which is why code review alone cannot catch this.
* **Polymarket, 2026-05-20.** Nine packages published inside two minutes by an account that simply took a
  brand name, with a postinstall script that prompted for a private key and also read `PRIVATE_KEY` from
  the environment and `.env` files.

The lesson is that the two failures need different controls. Injective needs pipeline hardening on the
producer side and integrity pinning on the consumer side. Polymarket needs the consumer to stop running
install scripts at all.

## Which of the six areas

Infrastructure and supply chain, primarily, with the seam right behind it, because the dApp build is
where these packages land. It also touches the wallet area, since the payload's target is always keys.

## Does this reach a normal web application, and how

**Yes, completely. This is not a web3 method at all.** It applies unchanged to npm and Composer
dependencies in WordPress and Laravel applications, to GitHub Actions workflows, and to developer


* Two of the nine Polymarket packages were named for AI coding assistants. He works with one. A plausible
  package name suggested mid task is exactly when this attack succeeds, so the discipline is to check the
  registry entry before installing anything a tool proposes.
* WordPress has its own version of the same pipeline: plugin auto updates pull code from a registry into
  production with no review step. Same shape, different registry.

## The safe way to look for it

All read only, and never install to find out:

1. Read the registry page: publish times, maintainer, version history, the `repository` field.
2. Download the tarball and read `package.json` and any install scripts in a text editor.
3. Diff the published artefact against the git tag it claims to come from.
4. Check the lockfile pins an integrity hash, and that the hash matches what is cached.
5. Grep the package for network calls inside functions that handle secrets or credentials.

## The control that catches a false positive

Postinstall scripts, telemetry files, and automated releases are all common and usually legitimate, so
none of them is a finding on its own. Escalate only on one of these four:

* a destination host assembled at runtime rather than written as a string,
* a secret travelling in a request, including in a header,
* a prompt for a secret during install,
* reading `.env` or credential environment variables.

Any one of those is decisive. None of them has an innocent explanation.

## Where else this shape appears

pip, composer, gem, cargo, and any registry without a binding between package names and brands. GitHub
Actions pinned by tag rather than commit SHA. Docker base images on floating tags. WordPress plugin and
theme auto updates. Browser extensions, which update silently and run in the page.

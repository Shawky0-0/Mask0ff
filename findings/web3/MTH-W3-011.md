# MTH-W3-011: every gate has two subjects, name them both out loud

**YZH runs no web3. This card is not a finding about the fleet.** Related:
W3DS-0028,
W3DS-0029,
MTH-W3-001.

## The technique in one line

At every permission check, write down separately who is asking and whom the request
is about, then confirm the code checks both, because it usually checks the easy one.

## The discovery signal

A function that takes a target as a parameter, and an authorisation condition next
to it that mentions only the caller. In web terms: an endpoint that receives a
`user_id` in the body and checks only the API key. The unchecked parameter sitting
beside a checked identity is the whole signal.

## The mechanism

An authorisation decision is not one question, it is at least two:

* **Who is asking.** Is this caller allowed to perform this kind of action at all.
* **Whom is it about.** Is this action allowed against this particular subject.

Code answers the first question naturally, because the caller is right there in
`msg.sender` or in the request context. The second question requires the developer
to notice that a target parameter exists and that it needs its own check. Nothing in
the language, the framework or the type system prompts that.

So the failure is not carelessness. It is that one question is handed to you and the
other has to be remembered.

There is a third question, and it is the one W3DS-0029 missed:

* **Which permission records did I read.** If standing is spread across an allow
  list and a deny list, checking one of them answers half the question and looks
  like a complete answer.

## Which of the six areas

Smart contract logic, where both source findings sit. But the class is not a
contract class at all.

## Does this reach a normal web application

**Yes, and this is the strongest transfer of the run.** It is broken object level
authorisation, the most common serious bug in real APIs, stated in the terms that
make it findable rather than in the terms that make it sound theoretical.

Concretely, on the YZH fleet:

* An internal service calls an endpoint with a service token and passes a customer
  id. The endpoint checks the token. It never checks that this service is allowed to
  touch that customer.
* An admin action takes a user id from a form field. The middleware checks the
  admin role. Nothing checks which users this admin may act on.
* A webhook handler trusts the signature on the message and then acts on the account
  named inside it. See MTH-W3-005,
  which is the same failure from the message side.
* A user is suspended in one table and still has an active API key in another.

## A safe way to look for it

Read only, on code the tester is authorised to read. No probing, no live target.

1. List every function or endpoint that acts on a named subject: an id, an account,
   a document, an address.
2. For each, write two lines. "Caller check: ___". "Subject check: ___".
3. Any line that stays empty is a hypothesis.
4. Then list every place a subject's standing is stored. If there is more than one
   place, check whether each gate reads all of them.

The value of writing the two lines separately, rather than reading the code and
judging, is that an empty line is visible and a missing thought is not.

## The control that catches a false positive

**The check may legitimately live one layer up.** If the only caller is a privileged
contract or a gateway that already validated the subject, the inner check is
redundant rather than missing. Read the caller before reporting.

Even then it is worth a note rather than nothing, because the guarantee now depends
on a component the audited code does not control, and that dependency is usually
undocumented.

The second control, for the two lists case: confirm the contradictory states can
actually coexist. If granting the blocked status automatically strips the approved
status, the single check is correct and there is no finding.

## Where else this shape appears

Impersonation and "log in as user" features. Batch and cron jobs acting over a list
of accounts. Support tooling. Multi tenant systems where the tenant id arrives in
the request. Anywhere an identity is trusted and then handed a target.

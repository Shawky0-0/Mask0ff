# MTH-W3-006: read your own incident runbook as the attacker's script

**YZH runs no web3.** This card is about incident communications and applies to any
product with users. Related:
W3DS-0013,
W3DS-0015,
MTH-W3-003.

## The technique in one line

Take the message the organisation would send during an incident, and treat it as a
phishing template the attacker gets to fill in, faster and louder than you can.

## The discovery signal

Any user facing instruction that combines **urgency**, **a destination**, and **an
unfamiliar action**. In the incidents Blockaid tracked in April 2026 the instruction
was "revoke your approvals" or "migrate your assets". On an ordinary web product it
is "reset your password", "verify your account", "download the new app",
"re authenticate", "confirm your details before the deadline".

The strongest signal of all: **the action is one the user has never done before.**
Familiar actions have a remembered path. Unfamiliar ones do not, so any plausible
page passes.

## The mechanism

Phishing normally has to manufacture three things: a reason, urgency, and an
expectation that a message will arrive. During an incident the victim organisation
supplies all three, publicly, at a known moment.

The attacker adds one cheap thing: a domain name that reads correctly. Blockaid
recorded five campaigns in April 2026 where a lookalike appeared within hours of the
protocol's own announcement, and in several cases the malicious link was posted in
the reply thread directly under the official post, or under the security vendor's
own alert. For one incident, nine coordinated retweets went out within six minutes.

The user cannot tell the difference, and the reason is structural rather than a
failure of attention. **Nothing binds "this instruction is official" to "this
destination is official".** The user was told to go somewhere new and do something
new by an organisation they trust, and every candidate page looks equally right.

Note the connection to the DNS case. In the registrar hijack the attacker did not
even need a lookalike, because the real domain pointed at their page. Same outcome,
one layer lower.

## Which of the six areas

**The seam**, and it is the least web3 thing in this folder. Nothing about it
requires a chain.

## Does this reach a normal web application, and how

**Yes, completely, and it is the item in this folder Ahmed could act on soonest.**
The education app fleet reaches users by email, by WhatsApp and through the CRM.
Every one of those channels has the same gap, and WhatsApp is worse than email
because a lookalike sender is easier to stand up than a lookalike domain and there
is no address bar at all.

The concrete exercise, with no target touched and nothing sent:

1. Get the actual incident and account recovery templates the fleet uses. If none
   exist, that absence is itself the finding.
2. For each, extract the destination and the action requested.
3. Derive the lookalike names an attacker would register from that template. Write
   them down defanged.
4. Check which are currently unregistered, using public WHOIS lookups only.
5. Report the gap: the templates that send users to a new place, and the lookalike
   names sitting unregistered.

**Register nothing. Visit nothing. Send nothing.** The deliverable is the list and
the recommendation, and it stays inside the lane's reading only rule.

## A safe way to look for it

Everything above is reading and public record lookups. The only judgement call is how
far to take the lookalike list, and the honest answer is: far enough to show the
pattern, not so far that it becomes a shopping list. Ten names make the point.

If a live check of the fleet's own DNS or certificate transparency records is wanted,
those are public records about domains YZH owns, and reading them is inside scope.
Anything pointed at a domain YZH does not own is not.

## The control that catches a false positive

The gap is **not** present when both hold: the organisation's incident guidance lives
only on a domain and a login the user already uses daily, **and** the predictable
lookalikes are already registered or monitored. Check the second one by looking, not
by asking.

Also rule out the case where there is no user facing recovery action at all, for
example an internal only system. Then there is nobody to phish and the card does not
apply. Say so rather than stretching it.

## Where else this shape appears

Every event that makes users anxious and expectant, security related or not: a data
breach notice, a billing system migration, a forced app update, a bank merger, a
school enrolment deadline, a payment failure notice. **The attacker never has to
create the urgency. You publish it.**

## What happened

The token has a restricted mode. In that mode only approved addresses are meant to
send, receive or burn the token.

One code path let the minter contract burn tokens and release the collateral
behind them. That path checked that the caller was the minter contract. It never
checked that the address whose tokens were being burned was approved. So an
unapproved holder could get a redemption through by going via the minter, which
is the ordinary way anyone redeems.

## Why it worked

The check that was there looked like a real check. It named a role, it read a
permission, it rejected anybody who was not the minter. Read quickly, it is
indistinguishable from correct code.

The gap is that a request has two parties and only one of them was examined. The
minter contract asking is not the same question as the account being burned from.
The code answered the easy question, which had an obvious answer, and skipped the
one that mattered.

This is worth naming plainly because Ahmed will meet it constantly and not on a
chain. It is the same bug as an internal API that trusts its own service token and
then acts on whatever account number the request body carried.

## The fix, and why the obvious fix is not enough

The mitigation is one condition: assert that the from address holds the approval,
in the same branch. The obvious fix, tightening who is allowed to be the minter,
does not touch the bug at all. The minter was supposed to be the minter. The
problem was never who was calling.

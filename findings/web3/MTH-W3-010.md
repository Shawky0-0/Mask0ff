# MTH-W3-010: watch the public certificate logs for your own domain

**YZH runs no web3. This card is not a finding about the fleet.** Related:
W3DS-0027,
W3DS-0015,
MTH-W3-003.

## The technique in one line

Every certificate issued for a domain is written to a public log, so watching that
log for your own domain tells you somebody else took it, on the day, for free.

## The discovery signal

A certificate for your domain appears, issued by an authority you do not use, at a
time when nobody on your team requested one. In the February 2026 campaign the
takeovers and the new certificates happened the same day, from Sectigo, Let's
Encrypt and Google Trust Services.

## The mechanism

Browsers only trust a certificate if it has been published to certificate
transparency logs. Those logs are public and append only. This exists so that a
certificate authority cannot quietly issue a certificate for somebody else's
domain without leaving a record.

The side effect is what matters here. An attacker who takes your domain must get a
certificate for it, or visitors see a browser warning and the fake site fails. To
get that certificate, they must publish it. So the attack that is invisible in your
own systems, because none of your systems were touched, is loudly visible in a log
anybody can read.

That is an unusual position to be in. The defender has a free, real time,
attacker mandatory signal.

## Which of the six areas

The seam, and infrastructure. It is a detection method rather than a vulnerability
class, which makes it the first detection card in this folder.

## Does this reach a normal web application

**Yes, completely, and it is not a web3 method at all.** Every domain the YZH fleet
owns is in these logs already. Nothing about the technique involves a chain, a
wallet or a contract. It applies identically to a WordPress property, a Laravel
application, and a company's mail domain.

It is also one of the few security controls that costs nothing and needs no access:
the logs are public, so this can be checked for a domain from outside it entirely.

## A safe way to look for it

Read only, no scanning, no probing. The logs are a public database and querying
them touches nothing belonging to the domain owner.

1. Search a certificate transparency log aggregator for the domain name.
2. List the issuing authorities that appear over the last year.
3. Write down which of those are expected: the hosting platform, the content
   delivery network, the mail provider, the load balancer.
4. Anything outside that list is a question, not yet a finding.
5. Set up an alert so the same check runs continuously rather than once.

For the fleet this becomes a standing control rather than a test: one alert per
domain owned, checked when it fires.

## The control that catches a false positive

**Most unexpected certificates are legitimate.** Content delivery networks, hosting
platforms, email services and preview environments all issue certificates for
customer domains, often under names nobody on the team recognises. Building the
expected issuer list first is not optional, because without it the alert fires
constantly and gets muted, which is worse than not having it.

The second control is a CAA record. It declares which authorities may issue for the
domain, which both reduces the noise and denies the attacker the padlock in the
first place. A domain with CAA set and an alert on violations is in a much better
position than one with an alert alone.

## Where else this shape appears

Any public, append only, attacker mandatory record. Public package registries,
where a malicious version must be published to be installed. Public DNS, where a
name server change is visible to anyone who looks. App store listings, where an
impersonating application must be listed to be downloaded.

The general move is to ask what the attacker is forced to make public in order to
succeed, and then watch that.

## What happened

In March 2021, COLDCARD firmware 4.0.1 shipped with a build configuration error. The production board
config set `MICROPY_HW_ENABLE_RNG` to 0, because the device supplies its own hardware RNG wrapper. But
libngu checked whether the macro was defined rather than whether it was enabled, so it bound to
MicroPython's Yasmarang pseudorandom generator instead.

Yasmarang is seeded from the MCU unique identifier, which is fixed, a SysTick counter with roughly
80,000 to 120,000 possible values, and RTC registers. It is not a cryptographic entropy source, and it
is deterministic once initialised. Effective seed strength fell from an intended 128 bits to about 40
bits on Mk2 and Mk3, and about 72 bits on Mk4, Mk5 and Q, where mixing from the secure elements
partially compensated.

On 2026-07-30, five years later, someone started brute forcing those seeds and sweeping the wallets. No
physical access to any device was needed. Coinkite shipped fixed firmware on 2026-07-31, and published
plainly that updating does not repair a seed that was already generated weakly.

## Why it worked

The mistake is two characters wide. `#ifndef MICROPY_HW_ENABLE_RNG` asks "is this name defined". Setting
it to 0 defines it. To the developer the flag said off. To the preprocessor it said present. The
fallback was selected, silently, in the one code path where silence is unacceptable.

What turned a build slip into a five year exposure is that the failure was invisible from outside. A
device with 40 bits of entropy produces seeds that look exactly like seeds with 128 bits. Nothing warns,
nothing logs, nothing fails. The only way to notice was to read the linkage or to watch coins leave, and
what happened was the second one.

The reseed limitation makes the ceiling lower than the entropy numbers suggest. The device hashes 40
bytes of secure element data with SHA256d, keeps four bytes, and the reseed replaces a single 32 bit
state word. The search space is capped at 2^32 regardless of how good the input material was.

## What the fix is, and why the obvious fix would not work

The obvious fix is "update the firmware", and it is the one thing that cannot work here. Firmware
updates fix future seed generation. They cannot add entropy to a seed that already exists. Every
affected user has to generate a new seed on fixed firmware and move their funds, which the vendor says
directly.

The code fix is to test the value rather than the definition, and to remove the fallback so that a
missing hardware source stops seed generation instead of quietly replacing it. The process fix is a
build test for exactly the case that broke: set the flag to 0 and assert which implementation gets
linked. A single test asserting "the hardware generator is the one in use" would have caught this in
2021.

# MTH-W3-003: Ask what the user sees, what the user authorises, and who can change the code in between

Related: W3DS-0006,
W3DS-0009,
MTH-W3-002.

## The technique in one line

Treat the served front end as a security boundary: check who can replace it, whether anyone would notice,
and whether the confirmation screen states what is actually being authorised.

## The discovery signal

Three questions, all answerable from outside with public data:

* **Who can move the domain.** No registry lock, no DNSSEC, a registrar account without hardware backed
  multi factor.
* **Whether a swapped bundle would fail.** No published build hash, no subresource integrity attributes on
  the served scripts, no content security policy worth the name.
* **Whether the confirmation is honest.** A signing or consent step whose wording does not name the exact
  action, the exact spender, and the exact amount. In web3 terms, a permit or approval presented as a
  "Security Update", a "Network Verification", or any kind of maintenance.

Any one of those is worth a hypothesis. All three together is the full setup of the CoW Swap incident.

## The mechanism

For a dApp the front end composes the transaction the user signs, so whoever controls the served
JavaScript controls what the wallet is asked to approve. The contracts can be flawless and it does not
matter.

On 2026-04-14, attackers used forged identity documents to get a registrar to transfer control of CoW
Swap's domain, pointed the A records at their own server, and served a pixel perfect clone carrying a
drainer. The drainer never asked for a private key. It generated ERC-2612 permit signature requests
labelled as a security step, and signing them granted broad authority to move tokens. About $1.2 million,
roughly 26 hours to recover the domain, and the team spotted the resolution anomaly within minutes, which
shows detection is not the bottleneck. The registrar controls the clock.

The second half of this method is the consent screen, and it generalises past DNS entirely. A signature
that grants spending authority looks, in a wallet prompt, much like a signature that proves who you are.
If the prompt does not spell out the difference, users cannot.

## Which of the six areas

Infrastructure for the front end hijack, wallets and signing for the consent half, and NFT for the
metadata variant, where the thing that changes underneath the user is the content rather than the code
(see W3DS-0009).

The web2 equivalents of the deceptive consent step are everywhere: an OAuth consent screen that understates
its scope, a checkout that hides a recurring charge, a "verify your account" flow that is really a
permission grant, a delete confirmation that does not say what will be deleted. The payload differs, the
test does not.

## The safe way to look for it

Entirely public, entirely read only:

1. WHOIS and registrar status for the lock flags, plus whether DNSSEC is enabled.
2. Public resolvers over time, and certificate transparency logs, for unexpected changes.
3. The served page's own integrity attributes and its content security policy header.
4. Fetch the production bundle from outside and hash it, then compare against the published build if one
   is published. If none is published, that is itself the finding.
5. Read the confirmation wording against what the request actually does.


## The control that catches a false positive

A DNS change is not a compromise, because migrations, CDN moves and provider changes all look like this.
Require a second signal before escalating: a served bundle whose hash does not match the published build,
or a confirmation whose wording does not match the action it performs. Equally, a missing registry lock is
a hardening gap rather than an incident, and should be reported as one.

## Where else this shape appears

Bonk.fun, 2026-03-11: the same attack, about $23,000 from about 35 wallets, which shows the technique is
cheap enough to use on small targets. Beyond that: any WordPress site whose registrar account can be
talked into a transfer, any checkout or consent flow, any OAuth screen, and any application whose front end
is served from infrastructure a third party controls.

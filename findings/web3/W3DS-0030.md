## What happened

The system delays privileged operations. You propose something, you wait, then you
execute it. Each proposal also has an expiry, so a stale proposal cannot sit around
and be executed a year later.

One of the things you can propose is a change to that expiry window. If the change
shortens the window, executing the proposal breaks. The code writes the new,
shorter window, then re checks whether the operation currently running is still
within its window, using the value it just wrote. The operation was queued under the
old, longer window, so it now looks expired and the whole thing reverts.

The result is that the operators can never shorten the expiry period through the
intended path.

## Why it worked

The extra check looks like caution. Verifying readiness a second time, after the
call, reads as belt and braces.

It stops being caution the moment the call in between is allowed to change what
readiness means. The second check is not confirming the first one. It is asking a
different question, because the rule changed under it.

The impact here is availability, not theft. A feature stops working. It earns an
entry anyway, because the shape is the point: this exact pattern with the sign
flipped, where widening a limit lets something through that should have failed, is
an authorisation bypass rather than a broken button.

## The fix, and why the obvious fix is not enough

The mitigation removes the repeated readiness check and keeps only the timestamp
assignment.

The obvious fix, capturing the old expiry into a local variable and checking against
that, would also work and is worse, because it keeps a duplicated check that now
silently means something different from the one at the entry. Two checks that look
identical and evaluate different state is how the bug got here in the first place.

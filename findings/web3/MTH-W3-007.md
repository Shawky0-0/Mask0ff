# MTH-W3-007: ask what the lookup returns when it finds nothing

**YZH runs no web3. This card is a testing technique, not a finding about the fleet.**

## The technique in one line

For every read that is keyed by something a caller controls, or that happens before the data is
written, ask what comes back on a miss, and then ask whether that value is distinguishable from a
real answer.

## The discovery signal

Two shapes, and both are visible by reading code rather than by running anything.

* A value is fetched by an identifier that arrived in the request, and there is no bounds or
  existence check on that identifier.
* A getter reads state that is filled later, in a second step, and nothing marks how far the filling
  got.

The tell is the absence of a failure path. A lookup with no "else" is the thing to stop on.

## The mechanism

Most containers answer a miss with a default rather than an error. A Solidity mapping or array slot
reads as zero. A dictionary get returns None or the supplied default. An unset environment variable
is an empty string. A left join gives you nulls.

The defect appears when that default is then used as data. Two independent cases in one sweep:

* **Bonzo Finance, 2026-07-11.** A committee identifier outside the valid range returned a zero
  public key. The attacker then supplied a zero signature. Zero is the identity element in BLS, so
  the pairing equation held and the fake price was accepted. About $9.05 million.
  W3DS-0017.
* **TraitForge, Code4rena 2024-07, M-01.** Reading entropy before the pool was written returned
  000000, and that became the NFT's traits.
  W3DS-0022.

Different corpora, different chains, different year. One shape.

## Which of the six areas

Seam first, since the verifying code usually sits at the boundary between an off chain input and
on chain logic. It also lands in NFT and contract work, and in plain web work, which is the point.

## Does this reach a normal web application, and how

**Yes, directly.** The web versions Ahmed can look for tomorrow:

* An API that resolves a signing key, an API client or a tenant from an identifier in the request,
  gets nothing, and continues with an empty value. Then an HMAC is compared against an empty secret.
* A role or permission lookup that misses and returns the zero value, where the zero value happens
  to be the most permissive role.
* Configuration read before it has loaded, so a limit is 0, a flag is false, or a price is 0.
* An SQL join that produces NULL and a comparison that treats NULL as passing.

## A safe way to look for it

Reading only, and on a target he owns.

1. Grep the code for lookups by request supplied key. In PHP, array access and `??`. In JavaScript,
   object indexing and `||` defaults. In SQL, left joins.
2. For each, find the failure path. If there is none, that is the candidate.
3. Exercise it: send a request naming an identifier that cannot exist, and see whether the response
   distinguishes "unknown" from "invalid". If both produce the same success path, write it up.
4. Exercise the system before it is configured: fresh install, fresh migration, before the setup
   step. See what answers.

No chain interaction, no probing of anything he does not own.

## The control that catches a false positive

A default is not automatically a bug. Three checks before it becomes a finding:

* Is the default actually reachable, or does something upstream already reject the input?
* Is the default value legitimate in that field? Zero can be a real price or a real trait.
* Does the request succeed end to end, or does it fail closed a step later for an unrelated reason?

If the answer to the last one is "it fails later", it is a note, not a finding, and worth saying so
plainly.

## Where else this shape appears

Anywhere a container answers a miss instead of raising. Also the near sibling: a value that is
present but degenerate, such as an empty string secret, a zero key, an identity element, or an empty
allow list that is read as "allow everything". Rejecting the degenerate value before any check runs
is the control that kills both.

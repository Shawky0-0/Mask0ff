## What happened

When you run a modern front end in development, the framework opens a WebSocket so the browser can
be told that a file changed. Nuxt's dev tools ride on that same socket, and use it to expose a set
of functions the dev tools user interface calls.

Those functions had no authentication. No token, no handshake, no check of where the connection
came from.

Two of them chain. The first writes the "open in editor" command into the dev tools options. The
second runs it. So an attacker who can reach the socket picks the command and then asks for it to
be run, on the developer's own machine.

## Why it worked

The assumption was that the socket was private because it listens locally. It is not.

The advisory names three ways in. Another process on the same machine. Anyone on the same network
when the server was started with the host flag, which people do to test on a phone. And, the one
that matters most, any web page open in the developer's browser, because a page can open a
WebSocket to any address including localhost, and without an origin check the server cannot tell
that page from the real dev tools.

So reading a news site in one tab while the dev server runs in another was enough.

## The fix, and why the obvious fix would not work

Update to 3.3.1, or turn dev tools off.

The obvious fix, "bind to 127.0.0.1 only", does not work, and that is the lesson worth keeping. It
closes the LAN path and leaves the browser path wide open, because the browser is on 127.0.0.1 as
far as the socket is concerned. The control that actually closes it is an origin check plus a
token, on the socket itself.

For Ahmed this is a QA scope point more than a web3 one. The development environment is part of the
attack surface, and a critical rated bug that only affects development is still a critical bug
about the machine where the keys live. Related:
W3DS-0010, where installing a dependency prompted the
developer for a private key, and MTH-W3-002.

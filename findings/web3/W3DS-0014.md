## What happened

Sign In With Ethereum is a login scheme. Instead of a password, the site asks the
user's wallet to sign a short text message, and the site works out which address
signed it. ERC-4361 fixes the format of that message so that everyone writes it the
same way.

The message contains named fields. `domain` and `uri` say which site the login is
for. `nonce` is a one time value the site issued. `issued-at`, `not-before` and
`expiration-time` say when it is good for. `chain-id` says which network.
`statement` is the human readable line the user reads.

The paper "Stealing Trust: Unraveling Blind Message Attacks in Web3 Authentication"
describes what goes wrong. The signature is checked and the fields are not. The
attacker gets to choose the contents of the message, so the attacker gets to choose
what the site believes about it.

The paper's other half is the display problem: the message shown to the user and the
message actually signed are not verified to be the same, so a user can be shown one
thing and sign another.

## Why it worked

Because "the signature is valid" feels like it answers the whole question, and it
answers half of it.

A valid signature proves one thing: whoever holds that private key signed these
exact bytes. It proves nothing about who the bytes were for, when they were made, or
whether they have been used before. Those are separate questions and each one has
its own field in the standard, precisely because they are separate.

If the site does not compare `domain` against its own name, a message the user signed
for a different site works here. If it does not check the `nonce` against one it
issued and then delete it, the same signed message works twice, which is a replay.
The specification says the nonce should be chosen per session with enough entropy to
prevent replay, and that is only true if the server actually checks it. If expiry is
not enforced, an old capture works forever.

The wallet side is the same failure from the other direction. If the signing prompt
shows a friendly summary rather than the message, the user's consent is attached to
something they never saw. The Fairyproof article names the phishing version: the
wallet does not check that the request origin matches the `domain` field, so a
lookalike site can ask for a signature that names the real one.

## What the fix is, and why the obvious fix would not work

The obvious fix is to use a library. It is most of the answer and it is not all of
it, because these libraries take the expected domain and the expected nonce as
arguments. Pass the domain from the request instead of from configuration and the
check compares the attacker's value against the attacker's value. It returns true
and it means nothing.

The fix that holds is a rule about where each value comes from. For every field the
site checks, the value it is compared against must come from the server, not from
the message. Write the verification function so that is visible on the page: the
expected domain is a constant, the expected nonce is looked up from a store and
deleted, the clock comes from the server.

That rule transfers beyond Web3 because it is the same rule that catches the JWT and OAuth
versions.

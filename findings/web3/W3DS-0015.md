**This record does not assert that any target runs Web3.** The mechanism is a registrar-account
problem and applies to any hosted site. Related:

## What happened

Squarespace acquired Google Domains in 2023 and migrated the accounts. During that
migration two factor authentication was turned off on migrated accounts, including
accounts where the owner had enabled it.

In mid July 2024 attackers ran password spraying against those accounts. Password
spraying is trying a small number of common passwords across a very large number of
accounts, which is quiet enough to avoid most lockout rules. Without two factor, a
correct guess was a full login.

With the registrar account, the attackers changed the DNS records so the domain
names pointed at their own servers. Compound, Celer Network and PendleFi users typed
the correct address, saw a page that looked correct, connected their wallets, and
signed transactions that emptied them. Blockaid identifies the code on those pages
as the Inferno draining kit.

## Why it worked

The domain name is the whole of a user's ability to tell a real site from a fake one.
Everything else the user checks, the branding, the layout, the URL in the address
bar, follows from the domain resolving to the right place. Whoever controls the DNS
records controls all of it.

So the registrar account is production infrastructure with the same blast radius as
the web server, and almost nobody treats it that way. It is usually created once by
whoever registered the domain, often on a personal login, and then forgotten.

The migration is what makes this entry worth keeping. The affected teams had done the
right thing: they enabled two factor. The control was removed underneath them by an
event they did not participate in, and nothing told them. That is a general lesson
about hardening. A control you enabled once is not a control you have; it is a
control you had on the day you checked.

The academic taxonomy places this cleanly. The arXiv survey "Software Supply Chain
Security of Web3" lists domain and hosting attacks as a front end layer attack
vector and cites BadgerDAO, $120 million in 2021, as the reference case. So this is
a recurring class rather than one bad week at one registrar.

## What the fix is, and why the obvious fix would not work

The obvious fix is stronger passwords. Password spraying does not care much: it
works because two factor was absent, not because the passwords were unusually weak.

The controls that hold are registrar lock, which blocks a transfer or nameserver
change without an extra step, and two factor that somebody actually verifies is on.
Both are free. Neither is exciting, which is why they are missing.

The one that catches the case this entry is really about is monitoring. If a DNS
record on a production domain changes and an alert fires, the window between hijack
and discovery is minutes rather than however long it takes a user to complain on
social media.

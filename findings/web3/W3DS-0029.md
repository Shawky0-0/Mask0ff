## What happened

The token keeps two lists. One says who is allowed to hold and move it. One says
who is blocked, so their tokens can be frozen and later redistributed.

Nothing stopped an address being on both lists. The burn check asked only whether
the address was on the allow list. A blocked address that was also allowed could
burn its own tokens, and could do so faster than an administrator could
redistribute them.

## Why it worked

The two lists were written by people solving two different problems. Somebody
built the allow list for the restricted mode. Somebody built the deny list for
freezing bad actors. Neither had a reason to think about the other, and the role
system happily stored both.

After that, correctness depends on every single gate remembering to ask both
questions. Most of them did. One did not, and one is enough.

The pattern to carry away is that the bug is not really in the burn function. It
is in a data model that permits a contradiction. The burn function is just where
the contradiction surfaced.

## The fix, and why the obvious fix is not enough

The mitigation adds the missing condition to the burn check.

The obvious fix, adding that condition, closes this instance and leaves the class
open, because the next gate added by the next developer will have the same choice
to make and no help making it. The fix that ends the class is at the model: make
blocked and allowed mutually exclusive by construction, so that no gate can read a
half truth even if it only asks one question.

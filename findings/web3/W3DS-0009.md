## What happened, or rather what the standard permits

There is no single incident here. This is a property of ERC-721 that a reader should understand before
any migration, and it is the reason NFT coverage in this folder is worth having.

`tokenURI(tokenId)` returns a string. That is the whole contract of the function. The token lives on
chain and is immutable. The thing people actually buy, the image or the document, usually does not: it
sits behind a URL, sometimes on a centralised server. Nothing on chain records what that content is
supposed to be, so nothing can detect it being replaced.

ERC-4906 added a `MetadataUpdate` event so a contract can announce that something changed. It carries no
new state. A consumer that receives it can only refetch and trust the answer, which is the same trust it
had before.

## Why it matters

Three failure modes follow directly, all described in the source.

A silent swap: whoever controls the host repins or replaces the file, and clients serve the new content
with no signal that anything happened. Cache inconsistency: marketplaces keep their own copies on their
own refresh schedules, so the same token legitimately shows different content in different places, which
issuer's server goes down, the collection falls over, because the on chain asset was never
self contained.

The unnamed 2024 case that circulates in secondary writing describes a compromised centralised host and
over 1,200 tokens whose images were changed, noticed only when owners tried to sell. It is recorded here
as context, not as a verified incident, because the source names no project and no date.

## What the fix is, and why the obvious fix would not work

The obvious fix is "use IPFS". It helps and it is not sufficient. Content addressing means the identifier
is derived from the content, so a change to the content changes the identifier. But if the contract
stores a mutable pointer, someone can point it at a different content identifier, and if nothing is
pinned independently the original content can simply disappear.

The fix that closes it is a commitment: store a hash of the metadata on chain alongside the pointer, so
any client can verify what it fetched is what the token promised. LSP4's VerifiableURI does exactly
this, and the useful detail is what it does not do. The chain stores and exposes the hash but never
fetches or enforces the remote file. Verification is the client's job, which means a client that skips
the check gets no protection from a standard that supports it. That is the same lesson as subresource
integrity on the web: the mechanism only helps if the consumer actually verifies.

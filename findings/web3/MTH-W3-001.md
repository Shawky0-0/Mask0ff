# MTH-W3-001: Split the two questions on every signed input

Related: W3DS-0004,
W3DS-0007,
W3DS-0005.

## The technique in one line

On every input that arrives with a signature, separate "is the sender authorised" from "is this value
possible", and find out which of the two the code actually asks.

## The discovery signal

A verification function that ends at the signature or the role check. Read the ingestion path top to
bottom, and if the last thing it does before acting on the value is confirm who sent it, stop there,
that is the finding.

Two supporting tells:

* **Documentation naming exactly one authorised address or sender.** That phrasing shows the design is
  leaning on identity. Whenever a system says "only X can call this", the interesting question is what
  happens when X is compromised, because the answer is usually "everything X says is believed".
* **A previous audit that patched an example.** Ostium's auditors wrote in November 2025 that a
  compromised forwarder could cancel any order or action, and said in the same breath that their list
  was not a complete enumeration. The example got patched. The class did not.

## The mechanism

Authorisation and plausibility are different properties, and checking the first tells you nothing about
the second. A system that only checks authorisation has no partial failure mode: the moment the
authorised party is compromised, coerced, or simply wrong, it accepts whatever it is told, without limit.

Three incidents this run are the same shape from three directions:

* **Ostium.** The signature was valid, so a Bitcoin price of $5,000 and then $60,000 in one transaction
  was accepted. About $23.75 million. Quoting the writeup: "Trust the signer, trust the price. There is
  no second opinion."
* **VerusCoin.** The receipt was cryptographically authentic and nothing checked that value was
  conserved, so a self consistent forged export was paid out. About $7.54 million.
* **KelpDAO.** The verifier was genuinely authorised and genuinely honest. It was reading the source
  chain through RPC nodes the attacker controlled, so it signed a true attestation to a false fact.

## Which of the six areas

The seam first, then bridges, then the contract layer. It is a seam method because in every case the
untrusted value entered from an off chain component that had been granted trust.

## Does this reach a normal web application, and how

**Yes, and this is the strongest transfer in the whole folder.** It is the signed webhook problem
exactly: the HMAC verifies, so the body is trusted, and nobody asks whether the amount is plausible.


* A payment or CRM callback whose signature checks out, carrying an amount, a plan, or a status nobody
  bounds.
* A JWT with a valid signature and a claim nobody validates against what the user may actually do.
* A partner API response trusted because it came from the expected host over TLS.

A price of 1, a quantity of 100,000, a date in 1970, a discount of 100 percent, a balance larger than
the business has ever held. Then follow what happens. If it lands, the system was only ever checking who
was speaking.

## The safe way to look for it

Read the ingestion path and write the checks down in order. Then ask which of these four is missing:

1. a bound against the previous accepted value,
2. a staleness window,
3. a second independent source, with a halt on disagreement rather than a choice between them,
4. conservation, meaning totals recomputed rather than accepted.

For contracts this is source reading only. For a web application it is source reading plus one request
sent as an authorised sender. Neither needs any chain interaction, and nothing in this lane may touch a
chain regardless.

## The control that catches a false positive

If any of the four checks exists, the hypothesis is dead, and it may exist further downstream than the
ingestion point, so follow the value to where it is used before concluding. Also confirm the endpoint is
not intentionally permissive: some feeds genuinely accept any value and bound it at consumption time,
which is a legitimate design.

## Where else this shape appears

Pull oracles. Keeper and automation networks. Anything named "trusted forwarder", including ERC-2771
style meta transactions. Cross chain verifiers. And in web2: every webhook, every payment callback,
every signed redirect, every SSO assertion, and every import file that carries its own totals.

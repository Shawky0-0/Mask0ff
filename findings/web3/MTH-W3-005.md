# MTH-W3-005: trace every claim to the party that chose it

**This card does not assert that any target runs Web3.** It is an authentication review method
and is not Web3-specific. Related:
W3DS-0014,
MTH-W3-001,
MTH-W3-004.

## The technique in one line

Take every field the server reads out of a signed or encoded blob, and for each one
write down who chose the value it is compared against: the server, or the sender.

## The discovery signal

Verification code shaped like this:

```
if (verify(message, signature)) {
    user = parse(message).address;
    createSession(user);
}
```

**The signal is the gap between line 1 and line 2.** If nothing between them compares
a field to server state, the code has proved that someone signed something and has
concluded that someone signed *this*, for *us*, *now*. Three different claims.

Second signal: a library call where the expected values are passed in as arguments.
Read where those arguments come from. `expectedDomain: req.headers.host` compares
the attacker's value against the attacker's value, returns true, and means nothing.

## The mechanism

A signature or a MAC answers exactly one question: did the holder of this key produce
these bytes. Every other question has to be answered separately, and each answer
needs a value the sender could not choose.

ERC-4361 is a good teaching example because it names all the questions as fields:

| Field | The question it answers | Compare against |
|---|---|---|
| `domain`, `uri` | was this meant for us | a server constant |
| `nonce` | did we issue this challenge, and is it unused | server side store, deleted on use |
| `issued-at`, `expiration-time`, `not-before` | is it still good | the server clock |
| `chain-id` | is it for the right network | a server constant |
| `statement` | did the user read what they signed | the text the wallet actually rendered |

Parse a field and trust it, and the check is circular. The paper "Stealing Trust:
Unraveling Blind Message Attacks in Web3 Authentication" names the display half of
the same problem: the message shown to the user and the message signed are not
checked to be the same, so consent attaches to something never seen.

## Which of the six areas

**The seam**, entirely. The bug lives in web application code on both ends. Nothing
about it is on chain.

## Does this reach a normal web application, and how

**Yes, completely; the same bug appears without any Web3 component.**
Direct equivalents:

* **JWT.** Signature verified, then `iss`, `aud` and `exp` ignored. A token minted
  for one service accepted by another.
* **OAuth and OIDC.** `state` not checked, so CSRF into the callback.
  `redirect_uri` not compared against the registered value. `nonce` not tied to the
  session.
* **SAML.** Assertion signature valid, audience and recipient not validated, so an
  assertion for another relying party is accepted.
* **Signed webhooks.** HMAC verified, then timestamp and delivery ID ignored, so the
  same payload replays forever. Stripe and GitHub both document this and it is still
  the common miss.
* **Signed cookies.** Integrity checked, expiry and scope not.
* **Licence keys and activation tokens.** Same shape again.

**Concrete first pass on an authorized codebase:** find every verification function, list its
fields in a two column table, and mark each as server chosen or sender chosen. Any
sender chosen row that gates a decision is a finding. This is a reading exercise on
source available within the engagement's authorized access.

## A safe way to look for it

1. Grep for the verification primitives: `verify`, `hmac`, `jwt.decode`,
   `hash_equals`, `siwe`, `ecrecover`, `validateSignature`.
2. For each hit, follow what happens with the payload afterwards.
3. Build the table: field, what it is compared against, where that value came from.
4. Mark every row where the compared value is derived from the request.
5. For the nonce or timestamp rows, check the deletion and the clock. A nonce that is
   generated but never stored is not checked. An `expires_at` nothing reads is not
   an expiry.

**No requests need to be sent to find any of this.** It is source review. If a live
check is wanted later, that is a separate authorisation decision under the lane's
gate.

## The control that catches a false positive

Two things rule it out. First, a maintained library called with constants from
configuration for every expected value: read the call site, not the import. Second,
a framework that enforces the check upstream, for example a gateway that pins the
audience before the application sees the token. Confirm the upstream check exists
rather than assuming the framework does it.

Third, a field that genuinely is informational and gates nothing. Say so plainly
rather than counting it.

## Where else this shape appears

Anywhere a system accepts a self describing blob from the outside and reads the
description: signed URLs, receipt validation from app stores, SSO of every flavour,
inter service tokens, and any code path whose comment says "we verified the
signature so the contents are trusted".

# MTH-W3-008: normalise both sides, or the gate never matches the door

**YZH runs no web3. This card is a testing technique, not a finding about the fleet.**

## The technique in one line

Wherever a protection is selected by matching a string, find the code that normalises the request
and the code that normalises the rule, and check they are the same function.

## The discovery signal

A configuration file where a human wrote the path, the role, the host or the file extension by hand,
and a matcher that transforms the incoming value before comparing. The moment the two transforms
are written in different places, they drift.

The strongest signal of all: an advisory that says "incomplete fix for" an earlier one. A fix
applied to one side of a comparison is exactly how this class comes back.

## The mechanism

Nuxt, CVE-2026-71315. Routes are matched case insensitively. A previous security fix lowercased the
incoming path but left the route rule keys as authored. A rule written for `/Admin/dashboard` was
compared against `/admin/dashboard` and never matched. The router still served the page, because
the router does not care about case. Everything the rule carried disappeared with it, including the
auth middleware. An anonymous request got the protected page and its server rendered data.

Rated 8.2 high. W3DS-0019.

The failure mode to notice is not the bypass. It is that the rule silently did nothing. Nobody gets
an error for writing a rule that never matches.

## Which of the six areas

Seam. A dApp front end is a web front end, and its route rules gate the same things.

## Does this reach a normal web application, and how

**Yes, completely. This is not a web3 method at all**, and it is the strongest transfer in this
run. The same shape lives in:

* nginx `location` blocks against a request the application later canonicalises differently.
* A WAF or CDN rule keyed on a path the origin normalises another way.
* Laravel or WordPress middleware attached by route name, with the URL matched loosely elsewhere.
* Allow lists and deny lists of file extensions, hostnames, email domains and IP ranges.
* Any comparison of a user supplied string against a configured one, where one side gets
  `strtolower`, `trim`, URL decoding or unicode folding and the other does not.

## A safe way to look for it

On a target he owns, read only, and it costs minutes:

1. List the protected paths from the configuration.
2. For each, request it logged out in altered forms: changed case, trailing slash added and removed,
   doubled slash, percent encoded characters, uppercase percent encoding, and a trailing dot.
3. Compare the responses to the canonical form. A protected page that renders under one form and
   redirects under another is the finding.
4. Then read the code from both ends: how is the rule key built, and how is the lookup key built.

Nothing here touches a chain and nothing was probed during this sweep.

## The control that catches a false positive

A 200 response is not a bypass on its own. Confirm three things:

* The body actually contains the protected content, not an empty shell that fetches data later and
  is refused then.
* The canonical form is genuinely refused, so there is a control to bypass.
* The account used is genuinely unauthorised, with no leftover cookie or cached session.

## Where else this shape appears

Any asymmetric comparison. Case folding is the easy one. The harder ones are unicode normalisation,
where two different byte sequences render the same glyph; percent encoding, where the proxy and the
application decode at different times; and path separators, where Windows accepts a backslash that
the rule never anticipated.

The durable lesson for QA, and it is the advisory's own third workaround: a route rule is a
convenience, not an authorisation boundary. Check the session inside the handler, every time, and
then a missed rule is a bug rather than a breach. Related:
MTH-W3-005, tracing every claim back to the party
that chose it.

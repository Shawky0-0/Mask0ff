## What happened

Oku Trade lets users place limit orders and stop orders that a keeper executes later
on their behalf. When the keeper executes, the contract works out the minimum amount
the user should receive, so that a bad swap can be rejected.

That minimum comes from an exchange rate, and the exchange rate is computed as
`(priceIn * 1e8) / priceOut`.

Solidity integers do not have fractions. Division throws away the remainder. So if
`priceIn * 1e8` is smaller than `priceOut`, the result is not a small number, it is
zero. The report's example is a token worth 0.00001137 dollars priced against an
asset worth 120,000 dollars.

The minimum amount is derived from that rate, so it is zero too. The check before
the swap asks whether the amount received is at least the minimum. Zero is at least
zero, so the check passes no matter what comes back.

A malicious keeper could then execute the swap with transaction data that sends the
output to their own address. The report states the impact plainly: "Users lose all
of their pending order output tokens held in the Bracket, StopLimit or OracleLess
contracts."

## Why it worked

The check was never removed and never bypassed. It ran, and it compared the right
two numbers. It just compared them against a bound that had quietly become
meaningless.

That is what makes this class hard to see in review. Reading the code, the guard is
present and correct. The bug is one function away, in the arithmetic that produces
the number the guard uses, and it only appears at input values nobody thought about
because they look absurd. A token worth a hundred thousandth of a cent against an
asset worth six figures is not the case anyone writes a test for.

The severity comes from the combination. Precision loss on its own is a rounding
complaint. Precision loss in the input to a safety bound turns the bound off.

## What the fix is, and why the obvious fix would not work

The obvious fix is more precision: use `1e18` instead of `1e8`. It helps and it does
not finish the job. It moves the point at which the rate rounds to zero further out,
so the degenerate case gets rarer. Rarer is not impossible, and a bug that only shows
up on extreme price ratios is exactly the bug an attacker will arrange to reach.

The fix that ends the class is refusing the degenerate result: require the computed
minimum to be greater than zero before proceeding. That converts a silent permissive
bound into a revert.

The general rule is the useful part. **A guard whose threshold is computed
is only as strong as the worst case of that computation.** When reviewing any check,
do not stop at "is the check there". Ask what the threshold is at the edges of its
inputs, and whether the check still means anything there.

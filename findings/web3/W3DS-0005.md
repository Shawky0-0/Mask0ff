# W3DS-0005: KelpDAO and LayerZero, the verifier's view of the chain was the attacker's


**Same incident as W3DS-0001, a different layer of
root cause.** W3DS-0001, written by hand earlier today, files this as "one verifier decided whether
a remote claim was true". That is correct and it is the configuration layer. This entry files the
layer underneath it: **why the one verifier believed a lie**. Two distinct missing invariants in one
incident, so two entries. **The loss figure also needs reconciling, see the note at the end.**

## What happened

Initial access was on 2026-03-06: a LayerZero Labs developer was socially engineered and session keys
were harvested. From there the attacker moved into the RPC cloud environment and patched running RPC
nodes in memory. The patched nodes returned correct data to LayerZero's own monitoring and tampered
data to the verifier network. Nodes the attacker could not reach were knocked offline, pushing the
verifier's queries onto the poisoned ones.

On 2026-04-18 the verifier attested to a message claiming 116,500 rsETH had been locked on the source
chain. No such transaction existed. The bridge released the funds, because from its point of view
everything checked out.

The contracts were audited and no bug was found in them, because there was no bug in them. Quoting
OpenZeppelin, what failed was "not contract code, but part of the broader operational and integration
setup around the bridge infrastructure".

## Why it worked

Two things had to be true, and both were configuration rather than code.

The bridge was set up with a single verifier, so one attestation was enough. And that verifier learned
what happened on the other chain from a single provider's RPC nodes. Compromise the nodes and you do
not need to forge a signature or find a contract bug. You tell the honest verifier a lie, and it signs
an honest attestation to a false fact.

The monitoring detail is the part worth carrying. The attacker did not disable monitoring, which would
have been noticed. They gave monitoring the truth and the verifier a lie, from the same process. Any
check that shares its data path with the thing being checked can be handled this way.

## What the fix is, and why the obvious fix would not work

The obvious fix is a better audit. It would have changed nothing, because the audit scope was the
contracts and the contracts were correct.

The fix is redundancy that does not share failure modes: more than one verifier, and independent RPC
providers underneath them, with a disagreement between sources treated as an attack rather than
something to average out. Add a withdrawal delay so a forged mint has to survive scrutiny. And move
monitoring off the production data path entirely, so it cannot be fed a curated view.

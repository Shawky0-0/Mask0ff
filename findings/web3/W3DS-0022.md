## What happened

TraitForge mints NFTs whose traits come from a pool of pseudo random values, the entropy. The pool
is filled in batches, in transactions after deployment.

The function that hands out the next entropy value did not check whether the pool had been filled
yet. Solidity reads unwritten storage as zero, so the function returned 000000 and did it without
complaint.

A user minting during that window paid for a token, received one, and got traits of zero. The
finding records the impact as users losing funds and airdrop eligibility.

## Why it worked

Nothing said "not ready yet".

The pool being empty and the pool holding a legitimate value of zero look identical from inside the
function. That ambiguity is the whole bug, and it is why the fix is a watermark comparison rather
than a check for zero: the contract knows how far it has been initialised, so ask that question
instead of guessing from the value.

## The fix, and why the obvious fix would not work

The recommended fix is one line: require that the slot being read is below the last initialised
index.

The obvious fix, "reject entropy that is zero", is worse than it looks. It rejects a legitimate zero
if zero is ever a valid trait value, and it still lets a partially filled pool serve garbage from
slots that happen to be non zero for another reason. Checking the watermark answers the real
question, which is whether this slot was ever written.

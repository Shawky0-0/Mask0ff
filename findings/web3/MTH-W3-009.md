# MTH-W3-009: test with two users, because a cache bug is invisible to one

**YZH runs no web3. This card is a testing technique, not a finding about the fleet.**

## The technique in one line

Write out the cache key in full, list every input the cached computation actually read, and if the
second list is longer than the first, you have found a cross user disclosure.

## The discovery signal

Any memoisation, caching or reuse in front of code that reads ambient state: the current request,
the session, the logged in user, a token, a tenant. The words to grep for are memo, cache, static,
singleton, lru, and any decorator that promises to skip work.

The second signal is procedural: a test suite where every test logs in as one user. A cache bug
cannot fail that suite. It has nowhere to show.

## The mechanism

hono, CVE-2026-71850. Its `memo()` helper decided whether it could reuse rendered HTML by comparing
the props passed in. Components that also read request scoped values, through JSX context or
`useRequestContext()`, were compared on a subset of their real inputs. Two users with the same props
on the same server instance shared one cached render. The advisory names the leaks: another user's
account and profile data, request specific secrets such as CSRF tokens, and content meant for
another role.

Request isolation worked correctly. The cache around it did not.
W3DS-0021.

## Which of the six areas

Seam. A dApp front end renders wallet addresses, balances and session state on the server, which is
exactly the material this leaks. But the technique is not web3 in any way.

## Does this reach a normal web application, and how

**Yes, completely, and it is the most immediately usable card in this folder for the QA lane.** The
same defect, in the fleet's own stack:

* A CDN or Varnish rule that caches a page containing the logged in user's name because the rule
  keys on URL and ignores the cookie.
* A WordPress object cache entry written without the user identifier in the key.
* A PHP static or a Laravel singleton holding request state on a long lived worker.
* A GraphQL or REST response cache keyed on the query and not on the token.
* Any "we added caching to fix the slow page" change, which is where these arrive.

## A safe way to look for it

Two browser profiles, ten minutes, on a target he owns:

1. Log in as user A in profile one and user B in profile two. Give them different names and
   different roles.
2. Load the page as A. Load the same page as B. Load it as A again.
3. Search B's HTML for anything belonging to A: name, email, account number, role specific
   controls, and above all the CSRF token.
4. Do it again with the cache warm, and again with both loading at the same time. A cold cache hides
   the bug, which is why a single careful pass can come back clean.
5. Repeat for pages served through the CDN, since the answer can differ from the origin.

Reading only. No chain interaction, no probing of anything he does not own.

## The control that catches a false positive

Anchor on a value that must differ per user. The CSRF token is the best one, because it has no
legitimate reason to repeat across sessions. Then check:

* Was it really two sessions, or one browser with a shared cookie jar? Separate profiles, not
  separate tabs.
* Is the shared content actually public? A shared header proves nothing.
* Does it reproduce? Once can be a screenshot of the wrong tab. Twice is a finding.

## Where else this shape appears

Every layer that can say "I have seen this before": the browser, the CDN, the reverse proxy, the
application cache, the ORM identity map, the memoised function, and the connection pool that hands
back a session with state still attached.

The rule that kills the class, and it is worth typing into the QA standard: **if you cannot write
the cache key out in full, you do not know what you are caching.** Make hidden inputs into visible
arguments, so they land in the key by construction. Related:
MTH-W3-007, which is the same discipline applied to
reads rather than to writes.

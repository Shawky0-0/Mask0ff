## What happened

A library used to create user identities in the browser had a function that made a
new key pair. You call it, you get a private key, and that key controls the
account and whatever it holds.

A change to the code broke the randomness. The function kept working and kept
returning a key pair. It just returned the same one to everybody. The advisory
names the resulting account identifier, which is how you know the output was fixed
rather than merely weak.

## Why it worked

There was no error and no warning. A key pair came back, it had the right shape,
and every test that checked "did I get a key" passed. The only test that fails is
one that asks whether two keys are different, and almost nobody writes that test
because it feels like testing that addition works.

This is the second time this folder has recorded the same class in three days. In
W3DS-0008 a firmware build check tested whether a flag existed rather than whether
it was switched on. Here a code change swapped a secure source for an insecure one.
Different mistake, identical outcome: the thing whose only job was to be
unguessable became guessable, and the system carried on normally.

## The fix, and why the obvious fix is not enough

The fix restores a secure source. The obvious fix, reviewing the diff more
carefully, would not reliably catch this class, because the diff looks harmless:
one source of bytes swapped for another. What catches it is the assertion that two
generated keys differ, run in continuous integration, where no reviewer's attention
is required.

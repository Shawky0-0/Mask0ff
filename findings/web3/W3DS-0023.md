## What happened

A dApp front end asks the wallet which chain it is on. It stores the answer. Later
it uses that stored answer to work out which contract address to send funds to,
because the same token has a different address on every chain.

If the user changes chain as part of connecting, the stored answer is from before
the change. The application then computes an address for the wrong chain. The
advisory's own example is a swap application deriving a wrapped token address and
sending the user's funds to the wrong place.

## Why it worked

Nothing here is broken cryptography or a broken contract. The application asked a
question once and treated the answer as permanent. The wallet is under the user's
control and the user can change it at any moment, including during the few seconds
the connection is being set up. So the answer had a shelf life of seconds and the
application used it for the rest of the session.

CWE-362 calls this a race condition, which is accurate but makes it sound rarer
than it is. The plainer statement is that the application and the wallet each held
a copy of the same fact and only one of them was allowed to change it.

## The fix, and why the obvious fix is not enough

The fix re reads the chain identifier from the provider rather than from captured
state. The obvious fix, refreshing the value when the wallet fires a chain changed
event, is not enough on its own, because the gap the advisory describes is inside
the connection flow, before the application is listening. The value has to be read
at the point of use.

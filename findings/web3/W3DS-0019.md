## What happened

Nuxt is a framework for building front ends, and dApp front ends are commonly built on it. It lets
you attach rules to routes: this page needs the auth middleware, this page is not server rendered,
this page gets prerendered.

The router treats paths as case insensitive, so /admin and /Admin are the same page. A previous
security fix made the lookup lowercase the incoming path. It did not lowercase the keys in the rule
table.

So a rule written for /Admin/dashboard sat in the table as /Admin/dashboard, the lookup arrived as
/admin/dashboard, and the two strings were never equal. The page still rendered, because the router
does not care about case. The rule attached to it simply vanished.

## Why it worked

The gate and the door were normalised differently.

Anything the rule was carrying went with it: the auth middleware, the client redirect, the decision
to turn server rendering off, the prerender rule, the payload handling. An unauthenticated visitor
got the page and the server rendered data inside it. The advisory rates it 8.2 high.

Worth noting for the study lane: this is the second attempt at the same bug. CVE-2026-53721 was the
first. A partial fix on one side of a comparison is how these come back.

## The fix, and why the obvious fix would not work

The fix makes both sides fold case the same way, and only when the router is configured case
insensitive.

The obvious fix, "write your route rules in lowercase", is a workaround and the advisory lists it
as one. It fails the moment somebody adds a rule with a capital letter, and nothing tells them.
The rule silently does nothing, which is the worst possible failure mode for a security control.

The real control is the third workaround, and it is the one Ahmed should carry into QA: the route
rule is a convenience, not an authorisation boundary. Check the session inside the handler.

## What happens

You POST a username that does not exist to `/wp-login.php`. WordPress builds an error
message saying so, and puts your username in it. If that username is shaped like
`< area onclick=...>`, the message comes back as live markup instead of text, and the
attacker's JavaScript runs in the site's own origin. **No login, no account, no plugin.**

## Why it works

Two functions are asked to make the input safe and they do not agree with each other.

`strip_tags()` looks at `< area` (bracket, space, tag name) and decides it is not a tag, so
it removes the bracket part and leaves what follows. Later, `wp_kses_post()` looks at what
survived and decides it **is** valid HTML, and lets it through as an allowed tag.

Neither function is broken. They just answer the same question differently, and the value
travels through both. The whitespace can be a space, a tab, a newline or a carriage return.

## Chaining it to code execution, and the honest limits

The chain is real and the preconditions are heavy. The XSS itself needs nothing. Getting
from XSS to PHP execution needs **all** of:

1. a **logged in single site administrator** who visits the crafted link,
2. Application Passwords enabled,
3. plugin upload available.

Then: the injected DOM hijacks the `user-profile` script that WordPress loads on the login
page for password reset, uses Same Origin Method Execution, steals an Application Password
from the administrator, uploads a plugin into `wp-content/plugins/`, and executes PHP as the
web server user.

**That is a social engineering step in the middle**, and it is fair to say so. The XSS is
unauthenticated. The RCE is not.

## The fix, and why the obvious one would not work

The obvious fix is to make the two sanitisers agree, or to add a third one. Both are wrong:
you would be guessing at every downstream consumer of that string forever.

The actual patch **escapes at the interpolation site**: `esc_html()` on the failed login
username in `wp-includes/user.php`, before it reaches either sanitiser. The value is HTML
encoded when it is placed into the message, so it does not matter what any later function
thinks it is looking at.

**That is the transferable lesson. Escape at output, where you know the context. Sanitising
at input assumes you know every path the value will take, and you never do.**

## CORRECTION TO THE VAULT, and it changes the remediation advice

The program plan and
the handoff both record, from 2026-08-10:

> Exploitable range 6.4 to 7.0.2, fixed in 7.0.3. The Hacker News line about "every version"
> is loose.

**Two things there are wrong.** Confirmed 2026-08-12 against two independent sources.

**1. The affected range is 4.7 to 7.0.2, every release on every branch.** Not 6.4. The
University of Toronto advisory states it plainly, and the disclosure describes the flaw as
present since 4.7. Versions 4.6 and earlier are end of life with no patch.

So **The Hacker News was substantially right and the vault was wrong to call it loose.** The
nuance is that the *reflected XSS* reaches back to 4.7, while the *unauthenticated
JavaScript execution in the WordPress origin* is described across 6.4 to 7.0.2. The vault
recorded the narrower number as if it were the whole picture.

**2. The fix is not only 7.0.3.** It is **7.0.3, 6.9.6, 6.8.7, and equivalent minor releases
on every supported branch back to 4.7.**

2026-08-10. If a site runs 6.8.x, the advice "only 7.0.3 fixes it" is wrong twice over: it
pushes an unnecessary major upgrade, and worse, someone reading "we are on 6.8, so 7.0.3 is
not our version" could conclude they are unaffected. **They are affected, and their fix is
6.8.7.**

**The right message is: update to the current patch on your own branch.** That is a small
update on every branch, not a migration.

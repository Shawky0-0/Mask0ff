# WPDS-0006: Demi, unauthenticated directory deletion through the restore step endpoint

**Read this one for the design, not the payload.** The interesting thing here is that the
unauthenticated endpoint is deliberate, and for a defensible reason. Related:
WPDS-0004,
MTH-WP-003,
the advisories folder.

**This entry carries more `___` than WPDS-0004.** The registration, the parameters and the
gates were read directly from the plugin source at two tags. The exact mechanism that makes
the deleted directory attacker controlled was NOT confirmed, and is marked as a hypothesis
below rather than stated. That distinction is the entry's most important feature.

## What happens

Demi restores a site from a backup. A restore replaces the database, and when the database is
replaced everyone gets logged out, including the administrator who pressed the button. So the
plugin keeps the restore going through an endpoint that does not need a login, authenticated by
a secret written to a file on disk.

That endpoint is `demi_restore_step`, and it is the one endpoint of the three this plugin
registers that anybody can reach. Wordfence report that it can be driven into deleting a
directory, without authentication, and rate it 9.1.

## Why the design is defensible and still wrong

It is genuinely hard to continue a privileged operation after you have destroyed the session
that authorised it. The author picked a real answer: a shared secret on disk.

The failure is what came next. The endpoint also accepts the workflow's state from the caller,
base64 encoded, and builds task objects from it. Once the caller supplies the state, the
caller is describing what the server should do, and the secret only controls who gets to
describe it.

## The open question, written down honestly

**How does an unauthenticated attacker get the token?** This run did not answer that. Two
gates were read in the source, `key` and `restore_step_token`, both compared with
`hash_equals()`, which is the correct comparison and not the weakness.

The hypothesis worth testing, and it is a hypothesis and not a finding: the same plugin has a
second advisory from the same week, **CVE-2026-15012, unauthenticated information exposure**,
in the same restore flow. An information exposure that reveals a token, feeding an endpoint
whose only gate is that token, is a complete chain. Two medium findings that are one critical
finding when you put them together.

That pattern is worth remembering on its own: **advisories are filed one at a time, and
attackers do not use them one at a time.**

## Why the obvious fix would not work

The obvious fix is to remove `wp_ajax_nopriv_`. That breaks the restore, which is why it was
there, which is why 0.0.7 did not do it.

The fix that holds is to stop letting the caller carry the state. Keep the workflow state
server side, keyed by the restore, and let the caller say only "continue", never "continue
like this".

## What this entry does not say

Whether any YZH site runs Demi. Gate `G5`, Ahmed's call. And it does not state the fix
invariant, because it was not established. That field is `___` on purpose.

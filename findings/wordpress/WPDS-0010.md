## B3 note, read this before treating it as a normal entry

This entry does not meet the dataset's own selection rules, and it is here anyway on a
stated exception.

It fails two of the five B3 criteria. The vulnerable build is not installable, because the
tags were purged. There is no fix to diff, because there was no fix, only a rollback.

It earns its place for a different reason. Every other entry in this folder teaches how a
developer's mistake becomes an attacker's route. This one teaches that the code can be
perfect and the account can be the hole, and it teaches the thing Ahmed's fleet actually
faces: plugins arrive from other people, and auto update is a trust decision made once and
then forgotten. **The reproducible part of this entry is the detection, not the
exploitation**, and that is the part written up.

## What actually happens

Somebody got into the plugin author's account. Not the plugin's server, not a site: the
account that publishes the plugin to WordPress.org.

They added a small function and released it as version 10.8.7. The function was wired to
run at the very start of every request, before WordPress had decided who you are. It looked
at the address for a parameter called `_wplogin`. If that parameter held the right value,
the function logged you in as an administrator of your choosing. No password.

The right value was checked against a fingerprint written into the plugin file. That
fingerprint shipped to every site. So it was never a secret, and the same key opened every
door.

About 20,000 sites had this plugin. Any of them that took the update automatically had the
door installed for them.

## Why it works

Because there is no step between "the author published it" and "your site is running it".
That is the whole point of the plugin repository, and it is genuinely a good thing most of
the time. It is also the reason one stolen password becomes 20,000 compromised sites.

The code itself is not clever. A hardcoded token check is the most obvious backdoor there
is, which is why an automated system spotted it in under two hours. Cleverness was not
needed, because the hard part was already done: getting the file onto the sites.

## The evidence trail, and the part worth stealing

The thing worth taking from this entry is how you confirm it from the outside, with no
access to anything.

The advisory says versions 10.8.7 and 10.8.8. Go to the plugin's tag list on SVN. The list
reads 10.8.0, 10.8.1, and so on up to 10.8.6, and then 10.8.9. The two versions named in
the advisory are not there. Ask for `tags/10.8.7/` directly and you get a 404.

Then read the changelog in 10.8.9. The vendor wrote that it is a re-release of 10.8.6, with
nothing changed but the readme and the version number.

Those two facts together tell you the whole story without a single word from a news site:
the releases were not fixed, they were deleted, and the vendor shipped the last clean build
again under a higher number. **A gap in a tag list is an incident record.** That is now
MTH-WP-008.

## What the fix is, and why the obvious fix would not work

There is no fix, and there could not be one. You cannot patch a backdoor out of a release
that should never have existed. The only correct response is to withdraw it.

The obvious hardening is "review plugin code before updating". For a fleet that runs dozens
of plugins releasing weekly, that is not a real control, and pretending it is one produces a
policy nobody follows. The controls that survive contact are duller: delay auto updates by
a short window, keep a file integrity baseline so a change is visible even when nobody
reads it, and log the parameter names arriving at the site so an invented one like
`_wplogin` stands out. PRISM's two hour detection is the argument that even a small delay
would have worked.

## What actually happens

The site has a registration form from this plugin, and the site owner has ticked "log the
user in automatically after they register". That setting is the whole precondition.

An attacker fills in the form with a username 61 characters long. The plugin's own checks
pass, because the plugin only asks two questions: is this name already taken, and does it
contain legal characters. Both answers are fine.

Then the plugin hands the name to WordPress core. Core has a rule the plugin does not
share: a username cannot be longer than 60 characters. So core refuses, and hands back an
error object rather than a new user number.

The plugin now does the wrong thing in the wrong order. It runs the number cleaner
`absint()` on that error object first, and only then asks "was this an error?". But
`absint()` on an object does not return zero or an error. It returns 1. So the error is
gone, replaced by a perfectly ordinary looking number, and the question "was this an
error?" is now being asked of something that is no longer an error.

The plugin believes it has just created user number 1. On almost every WordPress site,
user number 1 is the administrator who installed it. The plugin mints a one time login
token bound to user 1, puts it in the redirect URL, and hands it to the attacker. The
attacker follows their own redirect and is now the administrator.

## Why it works

Because a type cleaner ran before a failure check. That is the entire bug.

`absint()` is a good function. It is doing exactly what it says: give me a positive whole
number. The mistake is asking it that question about a value that might not be a number at
all. PHP will oblige, silently, and the silence is the problem. The error object carried
the message "this username is too long", and `absint()` threw that message away and
replaced it with the most dangerous possible integer.

## How you would reproduce it

In the lab, not anywhere else. Install 3.16.4, turn on automatic login, check that user 1
is an admin. Register with a 61 character canary username. Look at the redirect URL you
get back. If it has `autologin=true` and a `_wpnonce` on it, you have proved the bug
without logging in as anybody.

Then run the two negative controls before you believe yourself: a 59 character username
should behave normally, and the same request with automatic login turned off should
produce no token at all. If either control does not behave, your finding is about
something else and you have not found this bug.

## The fix, and why the obvious fix would not work

The vendor swapped two lines. `is_wp_error()` now runs before `absint()`.

The obvious fix is to cap the username field at 60 characters in the form, matching core.
That would close this specific route and leave the bug in place. `wp_insert_user()` can
fail for many reasons that have nothing to do with length: a duplicate email, a blocked
name, a filter added by another plugin that vetoes the registration. Every one of those
returns a `WP_Error`, and every one of those would still be turned into user 1 by the
unchanged code. Fixing the input validation fixes one way to reach the defect. Fixing the
order fixes the defect.

The second obvious fix, checking `if ( $user_id === 1 )` and refusing, is worse. It hard
codes an assumption about which user matters, it would break a legitimate first
registration on a fresh site, and it leaves the type confusion sitting there for the next
piece of code to trip over.

## Why this one matters more than its score

It is an AI plugin, and the vulnerable file is its MCP OAuth handler. Ahmed's fleet has AI
and RAG features. This is what the security surface of that work looks like in practice:
not a clever prompt, but an OAuth handler written to make an agent flow work, which quietly
turned off an authentication check for the whole site.

The bug is also a straight answer to a question worth asking about any AI integration: what
did this plugin have to weaken to make the agent protocol fit into WordPress? Here, the
answer is written down in one function.

## What actually happens

WordPress has a rule for its REST interface. If you turn up with only a login cookie and no
one time token, you are refused. That rule exists for exactly one reason: so a link cannot
act as you. If a cookie alone were enough, then any page on the internet could put a hidden
request to your site in it, your browser would attach your cookie, and the site would do
whatever the page asked, as you.

This plugin added a rule of its own on top. It said: if this request is my OAuth page, take
the login cookie and trust it directly.

The problem is how it decided whether the request was its OAuth page. It looked at the
address and asked whether the text `/mwai/oauth/authorize` appears anywhere in it.

Anywhere. Including in the part of the address after the question mark, which anybody can
fill with anything.

So an attacker writes a link to a completely different part of the site and staples that
text onto the end of it. The plugin sees its own text, decides this must be its OAuth page,
and trusts the cookie. The one time token is never asked for. The administrator clicks the
link, and the site acts as the administrator.

## Why it works

Because "does this string appear in the URL" and "is this my endpoint" are different
questions, and the code asked the easy one.

The URL is written by whoever made the link. The route is worked out by WordPress after it
has parsed the request. The plugin had the second thing available and used the first.

## The fix, and why the obvious fix would not work

Version 3.6.6 matches on the resolved route instead of the raw URL.

The obvious fix is to anchor the match: check that the URL *starts with* the OAuth path
instead of merely containing it. That is better, and it is still wrong. WordPress serves
REST under `/wp-json/`, or under `/?rest_route=`, or under a rewritten path, depending on
how permalinks are set up. Anchoring against one of those shapes breaks on the others, and
an attacker only needs one shape to work. Any answer built on the URL text is a guess about
URL formatting. The resolved route is not a guess.

The other tempting fix is to add a nonce check inside the OAuth handler. That protects the
OAuth handler and leaves the filter running on every other REST route on the site, which is
where the actual damage was.

## What happens

User Access Manager exists to stop the wrong people downloading the wrong files. To do that it
takes over file delivery: instead of the web server handing an upload straight to the browser,
the request goes through the plugin, which decides whether you are allowed it.

The request carries the file you want in a query parameter called `uamgetfile`.

The plugin turns that value into a WordPress attachment, checks whether you are allowed to see
that attachment, and then sends a file. In 2.3.15 the file it sends is not necessarily the
attachment it checked. Point the parameter far enough outside the uploads directory and the
plugin sends whatever is there, to anyone, with no login.

## Why it works

Because there are two different questions being answered by two different pieces of code, and
nobody made them agree.

`checkObjectAccess()` answers "may this user see post number 41". `FileHandler::getFile()`
answers "read the bytes at this path and send them". Both take their input from the same
string you supplied. Neither checks the other's work.

This is the same shape as WPDS-0001, where a
validation loop and an execution loop walked the same array and disagreed about it. Different
code, different plugin, same class of mistake: **the thing that was checked and the thing that
was used were not the same thing.** That is now two of the four entries in this folder, and it
is why MTH-WP-003 exists.

## How you would reproduce it

Install 2.3.15 on the sandbox, turn file protection on, and drop a text file containing a
unique marker somewhere outside the uploads folder. Ask for it through `uamgetfile` with
traversal. If the marker comes back, that is the finding.

Then, and this is the part testers skip, run the same request against 2.3.16 and confirm it
fails, and run a normal legitimate download on 2.3.15 and confirm it succeeds. Without those
two controls all you have is one request that returned something, which is not evidence.

## What the fix actually enforces

2.3.16 adds a function whose only job is to answer "is this path inside uploads", and it
answers it properly: `realpath()` both sides, then require the file to start with the uploads
directory plus a separator.

`realpath()` matters because it resolves the traversal before the comparison instead of trying
to spot it in the string. The trailing separator matters because without it a directory named
`uploads-evil` sitting next to `uploads` would pass.

## Why the obvious fix would not work

The obvious fix is to strip `../` from the parameter. That fails on encoded traversal, on
double encoding, on absolute paths, and on any encoding the next PHP version decodes slightly
differently. Filtering a string for badness is the same losing move as the denylist in
WPDS-0003.

The fix that holds compares the resolved path against the resolved boundary, because that
question has one answer and no encoding changes it.

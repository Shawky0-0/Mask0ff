## What happens

Gravity Forms has an older upload path that splits a file into chunks. Before it writes the
file it checks the extension against a list of extensions it refuses. That list did not
include `.phar`.

A `.phar` file is a PHP archive. It can contain PHP code. If the web server is set up to
hand `.phar` files to PHP, uploading one and then requesting it runs the attacker's code.
No login is needed to reach the upload path.

## Why it works

Because the check asks the wrong question. It asks "is this one of the bad ones", and the
list of bad ones was written by somebody who thought of `.php` and `.phtml` and stopped.
PHP has more than a few extensions that can be made executable, and a server administrator
can add more.

There is a second reason, and it is the one worth remembering: the word **legacy**. This is
the old chunked uploader. New code gets reviewed. Old code that still works gets left alone.
An attacker who reads a changelog and finds "new upload handler" immediately goes looking
for whether the old one is still reachable.

## How you would reproduce it

Licensed copy of 2.9.21.1 on a disposable box. Upload a `.phar` whose contents are a plain
text marker, nothing executable. If it lands with the extension intact, the denylist bypass
is proved. Stop there and read the server config to answer the execution question. Do not
drop a webshell to find out.

## Why the obvious fix would not work

The obvious fix is the one that shipped: add `.phar` to the list. That closes this report and
leaves the class open. The next extension nobody thought of is the next CVE.

The fix that holds is an allow list, plus not letting the web server execute anything in the
uploads directory in the first place. The second half of that is the stronger control,
because it does not depend on the plugin author being right.

## What actually happens

A contact form plugin lets you write things like "Thanks {name}, your entry is at
{thisPermalink}" in the confirmation email. So it keeps a lookup table: the word in braces
on the left, the thing to substitute on the right.

Most of the right hand sides are plain text taken from the submission. Three of them are
not. Three of them hold a function, to be run later, because the answer is not known until
the entry is saved. `{thisPermalink}` is one of those three.

Now the plugin fills the table with the submitted fields, using the field's name as the key.

If somebody submits a field whose name is literally `{thisPermalink}`, it goes into the
table at exactly the slot where the function was sitting, and pushes the function out.

Later, the plugin comes back to that slot, sees an entry it believes is one of its three
functions, and runs it.

Except it is now whatever the attacker typed.

## Why it works

Because the table holds two different kinds of thing and does not remember which is which.

At the moment the value is written, it is data. At the moment it is read, the code treats it
as an instruction. Nothing in between records that the value changed hands. `call_user_func`
does not know, and cannot know, that the string it was handed came from a form post rather
than from the plugin's own defaults.

Notice that no field validation would have caught this. The attacker's *value* can be
completely ordinary. The attack is in the field's *name*.

## How you would reproduce it

In the lab. Build a form, then submit it with one extra field whose name is
`{thisPermalink}` and whose value is `phpversion`.

Read the stored entry or the notification email. If the place where the link should be
contains a PHP version number instead, the string you submitted was run as a function.

That is the whole proof, and it does nothing to the site. Do not escalate it. You have
already demonstrated arbitrary invocation; picking a more dramatic function proves the same
fact and starts breaking things.

Run the control too: submit `thisPermalink` without the braces. It should be stored as
plain text. If it is not, your understanding of the bug is wrong and it is worth finding out
before writing it up.

## The fix, and why the obvious fix would not work

2.4.21 restores the three callable slots from the defaults before use, and adds a guard that
refuses to invoke anything that is not a static method reference.

The obvious fix is to reject field names containing braces. It closes the door and leaves
the room unlocked. The bug is that data and callables share a namespace; braces are just the
naming convention that happens to make the collision easy today. Change the placeholder
syntax tomorrow and the same defect walks back in wearing a different bracket.

The second obvious fix is `is_callable()` before invoking. That is worse than nothing here,
because it would pass. `phpversion` is callable. So is a great deal else. The test has to be
about where the value came from, not about whether it happens to be callable.

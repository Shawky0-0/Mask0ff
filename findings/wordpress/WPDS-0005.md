# WPDS-0005: BdThemes Biggopti, site takeover through a poisoned vendor data feed

**Exploited in the wild, and no plugin file was ever modified.** This is the most important
item the sweep has found so far, because the attack defeats the two controls most people rely
on: keeping plugins updated, and file integrity scanning. Related:
MTH-WP-004, the general method,
WPDS-0004, and
the advisories folder.

## What happens

Seven BdThemes plugins share a component that puts a promotional banner in the WordPress admin
dashboard. The banner text comes from BdThemes' own server. The script that draws it runs on
every admin page load, for every logged in administrator.

Somebody got write access to the storage bucket that serves that banner data and changed the
JSON. One field in the JSON, `display_id`, is written into an HTML attribute without escaping.
So the attacker's text stopped being text and became markup.

From there it runs as JavaScript inside the administrator's own session, and it does what an
administrator can do: creates a new administrator account through the REST API using the nonce
already present on the page, installs a plugin that is really a webshell, and drops two
must use plugins to keep access. One of those hides the new accounts from the user list and
adjusts the user count so the numbers look right.

**No plugin file was ever modified.** No update was required to become a victim.

## Why it works

Three decisions stacked up.

The plugin trusted its own vendor's API. That feels reasonable and it is the mistake. The
question is not "do I trust BdThemes", it is "can anything other than BdThemes ever put bytes
on that endpoint", and for a storage bucket the answer turned out to be yes.

The banner script ran on `admin_init`, unconditionally, on every admin page. So the blast
radius was every administrator, all the time, with no interaction needed.

And the value went into an `id` attribute unescaped while the identical value went into
`data-display-id` escaped. The author knew the rule. They applied it once.

## How the payload fired without a click

The injected value closes the `id` attribute and adds an `onanimationstart` handler plus a CSS
animation with a duration of about ten milliseconds. The animation starts on its own, the
handler fires, and nothing had to be clicked or hovered. Worth knowing as a tester: **"the user
would have to interact with it" is not a mitigation you can assume.** CSS can trigger a
handler by itself.

## The ARVE connection, and why it matters here

Wordfence state that the command and control domain in this campaign relates to the same threat
actors behind the Advanced Responsive Video Embedder and OptinMonster supply chain attacks of
the last two months.

That links directly to something else in this week's data. Wordfence separately list
**CVE-2026-18072, Advanced Responsive Video Embedder 10.8.7, unauthenticated authentication
bypass via a hardcoded backdoor in the `_wplogin` parameter**, CVSS 9.8. And the magic login
backdoor described in this BdThemes campaign is keyed on exactly `?_wplogin=<token>`. **Same
parameter name, same actor, two different vendors.**

Checked directly on the WordPress.org SVN repository on 2026-08-12: the ARVE tag list runs
10.8.0 to 10.8.6, then jumps straight to 10.8.9, with **10.8.7 and 10.8.8 absent**, and the
plugin's changelog.md has no entry for any of those three versions. That is consistent with a
poisoned release having been pulled, though no source read this run says so in those words.

The practical takeaway for a tester: `_wplogin` is now a string worth grepping for, and a gap
in a plugin's SVN tag list is worth a second look.

## Why the obvious fix would not work

The obvious fix is to escape `display_id`. That closes this one hole and leaves the pattern
standing: an administrator's browser still executes whatever a third party bucket decides to
send, and the next unescaped field is the next incident.

The fix that holds is to stop treating your own infrastructure as a trusted source. If the
banner must exist, render it as text.

## What this entry does not say

Whether any YZH or client site runs a BdThemes plugin, and whether any is compromised. Those
are gate `G5` judgements and they are Ahmed's. What this entry does say is that if the answer
to the first is yes, a clean file scan means nothing here, and the places to look are the user
table, the options table and mu-plugins.

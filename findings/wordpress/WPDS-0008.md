## What happens, in plain words

Somebody with an Author account uploads a file. It looks like an image. WordPress accepts it
and asks ImageMagick to make the thumbnails, the way it does for every upload.

ImageMagick does not trust the file name. It reads the first few bytes and decides for itself
what the file is. If those bytes look like PostScript, it hands the file to Ghostscript.

Ghostscript is not an image viewer. It is an interpreter for a programming language. So the
"image" is now a program, and it runs on the server.

## Why it works

The check and the parser disagree about what the file is.

WordPress checks the extension and the mime type. That is a check about the file's name. It
passes, because the file is called something ending in an image extension.

ImageMagick chooses its decoder from the file's content. That is a decision about the file's
bytes. The bytes say PostScript. So the decoder is Ghostscript.

One file, two answers, and the answer that runs code is the one nobody validated. This is the
same shape as MTH-WP-001: two pieces of code
reading the same input and reaching different conclusions.

## The two conditions, and why they matter more than usual

This one is not "patch and move on", because the version number is not the whole story.

The server needs Imagick, and it needs Ghostscript. Plenty of WordPress hosts use GD instead,
and on those the path does not exist at all. Ghostscript, though, is installed by default on
most Linux distributions, so on an Imagick host it is usually there.

That means a remote scanner cannot tell you whether a site is exposed. It can read the
WordPress version. It cannot see the PHP extensions or what is installed on the box. Anyone
who wants a real answer has to look at the server.

## How you would reproduce it

Local sandbox only, with Imagick enabled and Ghostscript present, on 7.0.3.

Upload a file whose leading bytes put it in the PostScript family and whose payload writes a
named marker to a temporary path. Then check whether that marker exists. That is the whole
proof: the marker exists, so the interpreter ran.

Run the negative control on a GD build and again with Ghostscript removed. If the marker
never appears anywhere, including where it should, the test has not proved anything except
that the upload never reached the image editor.

## What the fix is

Unknown at this level of detail, and marked `___` above rather than guessed. The release note
and the advisory record both say what the bug is and neither says what the patch does. The
wordpress-develop diff was not opened this run.

The obvious guess is that core stops handing PostScript family content to Imagick. Writing
that down as fact would be inference, not evidence, so it is not in the `fix.invariant` field.
That field stays empty until somebody reads the diff, and it is in the ledger as debt.

## What Ahmed can actually do about it today

Three things, and only the first is the patch.

Update core. The backport reaches every branch back to 4.7, so there is no site old enough to
be stranded.

Check the servers for Imagick and Ghostscript, because that is what decides whether the site
was ever exposed and no scan will tell you.

Check who holds `upload_files`. The default is Author and above. An LMS or membership plugin
that hands upload rights to students moves the bar from "a trusted contributor" to "anybody
who signed up", and that change is local, not something a core patch can fix.

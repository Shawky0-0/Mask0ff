**Exploited in the wild.** Confirmed by multiple vendors. This is not theoretical.

## What happens

A single anonymous POST to `/wp-json/batch/v1` reaches remote code execution on an
unpatched site. No account, no interaction from anybody.

## Why it works, and it is a two part chain

**Part one, CVE-2026-63030.** The batch endpoint takes a list of sub requests, validates
them all, then executes them all. Two loops, paired by position in an array.

When `wp_parse_url()` fails on one sub request's path, the code writes the error into the
validation array but forgets to write anything into the matches array. Now the arrays are
different lengths, and every entry after that point is off by one. **Request number three
gets dispatched to request number two's handler**, carrying validation that was never meant
for it.

**Part two, CVE-2026-60137.** A SQL injection in the `author__not_in` parameter of
`WP_Query`. On its own this reaches nothing unauthenticated, because parameter validation
stops it.

**The chain.** The desynchronisation is what lets the injection past the validation. Then
WordPress internals are used to create an administrator account, log in, and upload a
plugin. That is the shell.

Neither half is critical alone. Together they are pre authentication RCE.

## The part that matters most across an estate

**Patched does not mean clean.** The chain creates an administrator and drops a plugin. A
site that ran a vulnerable version after the public proof of concept appeared needs a
**compromise assessment**, not just an update.

## The transferable lesson

The bug is not in the SQL injection and it is not in the URL parser. It is in **pairing two
passes by array index across an error path.** Every framework that validates a collection
then acts on it has this shape somewhere.

If you only remember one thing: when you see validate all, then execute all, ask what
happens to the pairing when one item fails validation.

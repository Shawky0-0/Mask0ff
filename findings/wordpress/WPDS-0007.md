## What happens, in plain words

Bookly's booking form is a wizard. You pick a service, then a member of staff, then a time.
Each step is a separate call to `admin-ajax.php`, and the answers are kept in a session so
the next step can read them.

The staff step stores a list of staff ids. The time step reads that list back and asks the
database which slots are free. To ask, it builds a piece of SQL by gluing the list into the
text of the query.

Nothing turns those ids into numbers first. So whatever text you put in the list becomes
part of the query. That is SQL injection.

## Why it works

Three things line up.

The class that answers these calls turns its own CSRF check off. The method literally
returns `true` without looking at anything. It also declares every action anonymous. Both
choices are defensible for a public booking form. Together they mean an attacker needs no
account, no nonce, and no user to click anything.

The value survives a round trip through the session. Casting usually happens where a value
is read off the request. Here the value is read off stored state, and the code treats stored
state as already clean. It is not: the attacker wrote it one request earlier.

The sink looks safe and is not. The line uses `%s`, which every WordPress developer reads as
a placeholder. But the function around it is `sprintf`, not `$wpdb->prepare`. `sprintf` does
no escaping at all. It pastes the string in. The `%d` next to it really does force a number,
which makes the `%s` look like it belongs to the same protection. It does not.

## How you would reproduce it

Install tag 27.5 or 27.7 on the local WordPress sandbox. Never on anything else.

Call the first action to open a booking session and get a form id. Call the second action
with that form id and a staff id list that carries a conditional delay instead of a number.
Time both requests. Repeat each one enough times to see a distribution rather than a single
number, because a single slow request is usually the network.

Run the same pair against tag 27.8 as the differential control. If 27.8 is also slow, the
delay is not coming from the injection and the test is telling you nothing.

## What the fix is

Two `intval` casts, one at each end. The setter forces the property to an integer array the
moment anything writes it. The query builder casts again on the way out.

The vendor left a comment above the setter saying exactly why, and it names the whole bug in
two lines: the ids arrive unsanitised from the front end form data, and they end up in a raw
SQL `IN(...)` list in the slots finder. It is rare to get the invariant handed to you in the
patch. Take it when it happens.

## Why the obvious fix would not work

The obvious fix is to sanitise in the ajax handler, where the request comes in. That fails
the second time somebody adds a new entry point. There are seventeen actions on that class
and any of them could write to the chain. `setData()` is worse: it assigns any property by
name, with no checks at all, so a new caller can set `staff_ids` without ever going near the
setter that does the casting.

Putting the cast in the setter makes the type a property of the object rather than a habit
of the callers. Putting it at the sink as well means the query is still safe when somebody
inevitably bypasses the setter.

## The version disagreement, and what to do about it

Everything published says 27.5 and below. That reads as "27.6 is safe".

The code does not agree. `setStaffIds` stores the array raw at 27.5, at 27.6 and at 27.7. It
casts at 27.8, at 27.9 and at 28.0. `_prepareStaffData` matches: no cast at 27.5 or 27.6,
cast at 27.8 and 28.0. The vendor changelog backs this up, because 27.6 is a table redesign
and 27.7 is an appointments display fix. Neither mentions security. 27.8 says only that it
adds Divi widgets, and it is the release that carries the security fix.

**What I did not do.** I did not prove that 27.6 contains no fix of any other kind. I read
two files at each tag, the source and the sink named in the CERT reference list. A fix by
some third mechanism somewhere else in the plugin would not show up in what I read. So the
honest statement is: **the specific sanitisation that the advisory is describing is absent
from 27.6 and 27.7, and first appears in 27.8.**

That is Ahmed's call to make, gate `G5`, and it matters because Bookly is on the fleet. If
any site runs 27.6 or 27.7, a version check against the published range will report it
patched.

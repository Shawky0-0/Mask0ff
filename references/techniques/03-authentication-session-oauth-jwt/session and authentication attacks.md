# Authentication and Session Management Exploitation Playbook

## Research frame and attacker model

This report is a synthesis of standards, academic papers, vendor advisories, public CVEs, and disclosure corpora that index large volumes of bug bounty material rather than a claim that every individual public report was manually re-reviewed line by line in this response. Public indexing projects alone show the scale of the corpus: one HackerOne authentication-focused compilation contains hundreds of top auth reports, while a separate mirror of high-severity HackerOne disclosures spans 1,784 lines of entries. I used those corpora as navigational maps, then grounded the analysis in primary protocol texts, academic work on SSO, official vendor documentation, and selected public disclosures. [citation unavailable in inherited source]

Across modern web apps, APIs, SaaS products, mobile apps, and enterprise identity systems, the same offensive pattern repeats: the application accepts a proof of identity or session artifact outside the context in which it was minted. In practice, that means one or more of the following is missing: binding to the right user, tenant, device, issuer, redirect URI, session, audience, or lifecycle event. The recurring root causes documented across OAuth/OIDC, SAML, JWT, cookies, mobile deep links, and enterprise federation are mutable identifiers treated as trusted identifiers, front-channel parameters trusted too early, post-authentication artifacts not revoked aggressively enough, and insufficient separation between cryptographic verification and business-logic consumption. [citation unavailable in inherited source]

The highest-yield offensive mindset is therefore not “break the login page,” but “find where identity state survives a boundary crossing.” The most valuable boundary crossings are anonymous-to-authenticated session transitions, redirect-based handoffs, social-login merges, tenant onboarding, SCIM provisioning, mobile deep-link callbacks, token refresh, logout/reset/recovery, and enterprise trust transfer between IdPs, reverse proxies, and downstream services. This is exactly where modern incidents and fixes appear in the literature: OIDC mix-up and malicious-endpoint attacks, SAML signature wrapping, Entra cross-tenant claim confusion, ALB signer-validation gaps, middleware/header bypasses, refresh-token race conditions, and consent- or device-code-based account takeover chains. [citation unavailable in inherited source]

| Recurring offensive theme | What it really means in practice | Why it keeps paying |
|---|---|---|
| **Identity confusion** | A valid artifact is accepted for the wrong identity, issuer, tenant, or account merge. | Seen in OIDC issuer confusion, Entra `email`-claim misuse, social-login auto-linking, and SAML assertion wrapping. [citation unavailable in inherited source] |
| **Session continuity without fresh proof** | A pre-auth, old, or alternate-channel session survives into a stronger state. | This drives session fixation, logout bypass, stale-session reuse after password change, and 2FA-reset persistence. [citation unavailable in inherited source] |
| **Front-channel trust overreach** | Browser-visible or user-controlled inputs influence security-critical server decisions. | Classic sources are `redirect_uri`, custom headers, deep links, Host/origin handling, and login callbacks. [citation unavailable in inherited source] |
| **Bearer-token fragility** | Whoever gets the token gets the authority, unless sender-constrained revocation and audience checks exist. | This is why token leaks, refresh-token replay, consent abuse, device-code phishing, and redirect leaks are so dangerous. [citation unavailable in inherited source] |
| **Trust transitivity** | An upstream trusted component is assumed to have fully authenticated the user, so downstream validation is skipped. | High-value examples include ALB/OIDC headers, enterprise federation, and cloud IAM trust policies. [citation unavailable in inherited source] |

## Core web and API failure patterns

The most important practical distinction is between **proof-of-identity bypasses** and **proof-of-state bypasses**. Proof-of-identity bypasses let attackers authenticate without the legitimate secret or factor. Proof-of-state bypasses let attackers inherit, replay, persist, or redirect a state that was once valid. Modern bug bounty programs increasingly pay more for proof-of-state flaws because they chain cleanly with phishing, XSS, host-header abuse, social login, support tooling, or mobile token theft. OWASP’s session guidance, API2:2023, and logout testing guidance all point to the same operational lesson: if session IDs, reset artifacts, refresh tokens, or cookies are not aggressively rotated and invalidated, identity hardening on the login page is only partial protection. [citation unavailable in inherited source]

| Technique family | Technical explanation and root cause | Exploitation methodology and attacker vs victim workflow | Severity, detection, and representative cases |
|---|---|---|---|
| **Authentication bypasses, authentication logic flaws, alternate-channel bypasses** | The server trusts an execution branch that was never meant to be externally reachable. Typical root causes are cache fallbacks, internal headers, middleware bypass, feature flags, delegated-auth shortcuts, or parameter parsing inconsistencies. | The attacker looks for non-primary paths to a post-auth state: internal headers, alternate login handlers, special parameters, legacy endpoints, or proxy-specific routes. The victim may do nothing at all. | Usually **critical** because compromise is immediate and often silent. Real cases include the Next.js middleware bypass via `x-middleware-subrequest` and Okta’s delegated-authentication cache flaw for usernames above 52 characters. [citation unavailable in inherited source] |
| **Session management flaws, session fixation, session confusion** | The application fails to rotate session identifiers on privilege change, or fails to bind session state to the correct user journey. Root causes include keeping the same ID before and after login, attaching MFA/verification state to the browser session instead of the user, or allowing one user’s pre-auth state to become another user’s authenticated state. | The attacker pre-seeds a session ID, gets the victim to authenticate into it, or races state transitions so the wrong principal inherits the stronger state. In session confusion, the attacker and victim workflows collide in one browser or one callback chain. | Usually **high to critical**. Detection is often **moderate** because traffic looks like normal login activity. OWASP documents fixation; public reports describe fixation issues on Shopify, Acronis, and Enter. [citation unavailable in inherited source] |
| **Session invalidation issues, logout bypasses, stale-session reuse** | The server treats logout as cosmetic or local to one front-end context, while the session remains valid in the backend or for API calls. Similar failures happen after password change or password reset. | The attacker steals or already holds a session cookie/token, waits for the victim to “secure” the account, then continues using the old artifact. The victim believes the account is safe because the UI shows logout or password change success. | Often dismissed as “low,” but in admin, finance, support, or enterprise SSO contexts it is effectively **account takeover persistence**. OWASP explicitly requires secure session termination, and public cases show sessions surviving logout or password change. [citation unavailable in inherited source] |
| **Password reset flaws, account recovery abuse, recovery-channel downgrade** | Reset and recovery flows become weaker authenticators than the primary login flow. Root causes include reusable or long-lived reset artifacts, reset links that are not single-use, lack of MFA-strength parity, failure to invalidate sessions, and support or recovery paths that rely on weaker evidence than the account’s current assurance level. | The attacker attacks the recovery channel rather than the main login: captures or reuses reset links, abuses support-driven recovery, races reset artifacts, or forces an account into a weaker recovery state. The victim often only notices after lockout or suspicious notifications. | Frequently **critical** because recovery is a designed way to mint fresh authority. OWASP requires reset controls to be random, single-use, and securely expired, and public reports continue to show full ATO in reset flows and stale-session persistence after reset. [citation unavailable in inherited source] |
| **Email verification bypasses, phone verification bypasses, invite-system abuse** | Verification artifacts are bound to the wrong thing: the browser session instead of the email/phone, the invite instead of the target user, or the team membership instead of the account owner. In phone/SMS flows, OTP design is further weakened by SIM-swap and PSTN risk. | The attacker verifies their own artifact but causes it to confirm the victim’s identity, reuses a session token across “future” accounts, or receives access through a flawed invitation or team-enrollment flow. | The business impact is **high** because these flows often create the account, establish team access, or activate the first session. OWASP now treats email handling as an identity-system risk in its own right, NIST/OWASP warn about SMS/PSTN restrictions, and public reports show email-change verification failures and phone/session creation flaws. [citation unavailable in inherited source] |
| **API authentication flaws, HMAC/signature weaknesses, cross-origin auth flaws** | API auth fails when secrets are replayable, signatures omit critical parts of the request, timestamps/nonces are weak, or browser-facing APIs rely on permissive CORS with cookies/credentials. Another common design flaw is placing auth decisions in client code or edge middleware rather than the API itself. | The attacker replays valid HMAC/auth material, tampers with unsigned request components, steals browser-readable responses cross-origin, or talks directly to APIs while skipping the browser’s auth checks. | Often **critical** because APIs expose the same or greater authority than the web UI. OWASP API2:2023 frames this as broken authentication; public disclosures include HMAC signature forgery/replay cases and cross-origin credential exposure scenarios. [citation unavailable in inherited source] |
| **Cookie security weaknesses and token leakage** | Auth breaks when cookies lack `Secure`, `HttpOnly`, or appropriate `SameSite`, or when bearer tokens appear in URLs, redirects, logs, deep links, or browser-history-visible front channels. | The attacker hunts where auth material leaves the server’s intended channel: redirects, `.netrc`/client interactions, deep links, console snippets, referers, third-party redirects, or browser-readable storage. | Usually **high** because leakage converts a strong auth event into bearer-token theft. MDN and the cookie specs document the right controls; modern real-world leaks include OAuth bearer-token redirect leakage in curl and token theft via mobile magic-link deep links. [citation unavailable in inherited source] |
| **Race conditions in authentication** | Security checks and state updates are not atomic. The canonical issues are OTP/2FA reset races, email-verification races, and refresh-token reuse races. | The attacker sends parallel requests at the exact boundary where the server validates and then mutates state. Victim interaction may be absent or minimal, depending on the flow. | These range from **high** to **critical** because they let one valid artifact be redeemed multiple times or in multiple identities. PortSwigger treats races as business-logic flaws, and public cases include HackerOne’s 2FA reset race and email-verification race disclosures. [citation unavailable in inherited source] |

A representative **header-based authentication bypass** looks like this. The following request models the class of failures exemplified by the Next.js middleware CVE, where the application trusted a header that should have remained internal. [citation unavailable in inherited source]

```http
GET /api/admin/users HTTP/1.1
Host: target.example
x-middleware-subrequest: middleware:middleware:middleware:middleware:middleware
Cookie: session=lowpriv-or-empty
```

A representative **session fixation** chain looks like this. The logic failure is not stolen credentials; it is failure to rotate `sid=A` when the victim moves from anonymous to authenticated. OWASP explicitly defines this class, and multiple public reports show it in production systems. [citation unavailable in inherited source]

```text
Attacker                    Victim                         Application
   |                           |                                  |
   | GET / -> sid=A            |                                  |
   |-------------------------->|                                  |
   | send victim a link        |                                  |
   | with sid=A                |                                  |
   |                           | GET /login (sid=A)              |
   |                           |--------------------------------->|
   |                           | POST credentials (sid=A)        |
   |                           |--------------------------------->|
   |                           |   server authenticates sid=A    |
   | reuse sid=A               |                                  |
   |------------------------------------------------------------->|
   |            now operating with victim's authenticated session |
```

The offensive takeaway is simple: **treat every state transition as a privilege transition**. If a system does not regenerate identifiers, rebind state to the authenticated principal, and invalidate old artifacts across all channels, a bypass in practice is only a matter of finding the right alternate edge.

## Federation and token-protocol exploitation

Federated authentication vulnerabilities are rarely “crypto broken” in the simplistic sense. They are usually **context-binding failures around otherwise valid cryptography**. The identity token, authorization code, assertion, or signature is often valid in the abstract; what fails is the relying party’s ability to prove that the artifact came from the right issuer, for the right audience, for the right client, using the right redirect URI, in the right flow phase, with the right subject/account linkage. This is exactly the lesson from the OIDC and SAML research corpus: OIDC suffered from mix-up and malicious-endpoints classes, while SAML repeatedly failed at the interface between signature verification and claims processing. [citation unavailable in inherited source]

| Technique family | Technical explanation and root cause | Exploitation methodology and attacker vs victim workflow | Severity, detection, and representative cases |
|---|---|---|---|
| **OAuth vulnerabilities, OAuth redirect_uri exploitation, consent abuse, scope escalation, PKCE weaknesses** | OAuth breaks when the client or AS does not exactly validate `redirect_uri`, does not bind `state` strongly, allows dangerous redirect carry-over, or normalizes overbroad scopes into a single long-lived delegated grant. PKCE protects code interception in public clients, but it does **not** replace exact redirect validation, issuer binding, consent governance, or audience verification. | The attacker poisons or abuses the authorization request, gets the victim to approve a malicious app, or forces the client to accept a callback or scope expansion it should never have accepted. In many enterprise cases the victim completes MFA on the real IdP, which makes post-consent access look “legitimate” unless app governance exists. | Usually **critical** when the grant yields mail, file, admin, or refresh-token access. RFC 9700, RFC 7636, Google’s redirect-uri guidance, PortSwigger’s hidden OAuth vectors, and Microsoft’s consent-phishing guidance all reinforce these failure classes. [citation unavailable in inherited source] |
| **OpenID Connect vulnerabilities, IdP misconfigurations, single sign-on flaws, federation trust issues** | OIDC adds identity on top of OAuth, so token validation mistakes are more damaging. The classic failures are missing `nonce`, issuer confusion/mix-up, malicious discovery endpoints, dynamic-registration abuse, and trusting human-readable claims as identity anchors. Official OIDC and later RFC work added or strengthened `nonce`, issuer identification, and mix-up countermeasures because the original designs were exploitable in multi-IdP settings. | The attacker becomes or controls an IdP, a discovery endpoint, or a registration path; manipulates discovery metadata; or makes the RP send a code/token to the wrong issuer. Victims often just click a normal “Login with X” button. | This is often **critical** in SaaS because one successful SSO bug equals full app access. The OIDC evaluation paper introduced IdP Confusion and Malicious Endpoints attacks, found 75% of referenced libraries vulnerable to at least one single-phase issue, and RFC 9207 later standardized `iss` as an explicit mix-up countermeasure. [citation unavailable in inherited source] |
| **SAML attacks** | SAML’s biggest recurring problem is not “signed vs unsigned” but **what exactly got signed, what got parsed, and what the business-logic layer actually consumed**. XML Signature Wrapping and parser differential bugs let attackers keep a valid signature nearby while getting the service provider to process attacker-selected claims. | The attacker obtains any signed assertion from the IdP, rewrites the XML structure so a valid signature still verifies, and then causes the SP to process a different assertion, subject, or attribute set. In parser-differential cases, two XML parsers disagree on document structure. | Historically and still today this is **critical** because it becomes direct admin impersonation or cross-account login. The original USENIX paper found 11 of 14 major frameworks vulnerable; later real-world CVEs hit ruby-saml/GitLab and Node-SAML in precisely this family. [citation unavailable in inherited source] |
| **JWT attacks, JWT signature confusion, JWKS abuse** | JWT libraries fail when they trust attacker-controlled header parameters (`alg`, `jku`, `kid`, `jwk`, `x5u`) or mix token types and validation rules. The root cause is almost always “the verifier inferred security policy from attacker input.” | The attacker swaps algorithms, injects a remote JWK set, abuses `kid` lookups, or reuses a JWT minted for one purpose or audience in another context. A particularly common operational failure is letting the application fetch keys from attacker-controlled URLs. | Often **critical** because session or API auth is reduced to token forgery. RFC 8725 was published specifically to address these implementation pitfalls, and practical labs and guidance still include algorithm confusion and `jku`/`kid` exploitation as live attack patterns. [citation unavailable in inherited source] |
| **Refresh token abuse, access token misuse, token replay attacks** | Bearer tokens authenticate possession, not legitimacy. Without sender-constraining or immediate family invalidation, stolen access/refresh tokens remain useful until expiry or manual revocation. Rotation helps, but if reuse checks are not atomic or revocation is weak, replay is still exploitable. | The attacker steals a refresh token, device-code grant, consent-based grant, or bearer token and uses it before or after the legitimate client. The victim may never notice until the session is revoked or new devices appear. | Usually **high to critical** because these artifacts preserve access after the user’s interactive login. Auth0 and Okta explicitly document rotation and reuse-detection needs; RFC 9449 adds DPoP sender-constraining; Keycloak still had a refresh-rotation TOCTOU bypass in 2026. [citation unavailable in inherited source] |
| **Social login flaws, account linking vulnerabilities, identity-claim confusion** | The failure mode is merging identities on a mutable or insufficiently verified attribute, usually an email address. In the worst case, a user-created local account and a federated account become the same account even though only one side actually proved mailbox ownership or the IdP’s email claim is not globally trustworthy. | The attacker signs up first with the victim’s email, changes a profile email before verification, or uses a social login that returns an unverified or mutable email claim. The victim later logs in with Google/Microsoft/etc. and gets merged into the attacker-controlled account state. | Often **critical** and ideal for **pre-account takeover** because the attacker can plant persistence before the victim ever registers. OWASP now treats email normalization/verification as an identity-system problem; Clerk documents linking only after verified email, and public writeups plus advisories continue to show this pattern. [citation unavailable in inherited source] |

A representative **OIDC mix-up** / **issuer confusion** chain looks like this. The victim uses a normal login button; the bug is that the RP can no longer prove which AS issued the code. The OIDC evaluation paper formalized this, and RFC 9207 later added `iss` to the authorization response as a concrete countermeasure. [citation unavailable in inherited source]

```text
Victim -> RP: start login
RP -> Attacker-controlled discovery / metadata: learns endpoints
RP -> Victim: redirect to attacker-selected auth endpoint
Victim -> Honest IdP: authenticates normally
Honest IdP -> RP: returns code/state
RP (confused about issuer) -> Attacker endpoint: redeems code / treats attacker as issuer
Attacker -> RP or token endpoint: harvests or replays resulting authority
```

A representative **JWT JKU injection** looks like this. Practical exploitation still works whenever the server fetches verification keys from URLs specified by the attacker-controlled JWT header. [citation unavailable in inherited source]

```http
GET /api/admin HTTP/1.1
Host: target.example
Authorization: Bearer eyJhbGciOiJSUzI1NiIsImprdSI6Imh0dHBzOi8vYXR0YWNrZXIuZXhhbXBsZS9qd2tzLmpzb24iLCJraWQiOiJhdHRrMSJ9...
```

A representative **OAuth redirect and session-poisoning** issue is not just open redirect. The deeper problem is the server carrying or reusing request parameters across phases in a way that lets the attacker steer post-auth state or steal codes/tokens. Exact-match redirect validation, strict state binding, and refusal to inherit untrusted parameters across phases are the minimum baseline. [citation unavailable in inherited source]

## SaaS cloud and multi-tenant trust failures

Modern SaaS and enterprise auth failures increasingly happen **after** the IdP says “yes.” The attack surface is the glue: tenant discovery, app galleries, reverse proxies, SCIM, cloud trust policies, shared issuer URLs, device-trust claims, and role- or group-propagation pipelines. In other words, the dangerous question is no longer only “who authenticated?” but “what did all downstream systems infer from that authentication?” Public research on Entra `email`-claim confusion, AWS ALB signer validation, AWS OIDC trust-policy conditions, and SCIM provisioning takeover shows that modern offensive identity work is frequently a trust-translation problem. [citation unavailable in inherited source]

| Technique family | Technical explanation and root cause | Exploitation methodology and attacker vs victim workflow | Severity, detection, and representative cases |
|---|---|---|---|
| **Cross-tenant authentication flaws** | The SaaS app treats a claim like `email`, `preferred_username`, or a directory attribute as if it were a globally verified, immutable identity key across tenants. In multi-tenant Entra scenarios, that assumption is false. | The attacker creates or controls an account in their own tenant, sets a claim value that collides with the victim’s email, then uses “Login with Microsoft” against a SaaS app that auto-merges on email. The victim may never interact until after compromise. | This is one of the cleanest **full ATO** patterns in enterprise SaaS because it can bypass MFA and conditional access by authenticating as the attacker in their own tenant first. Descope documented nOAuth, Okta warned customers, and Microsoft’s claims-validation guidance emphasizes validating tenant/subject/actor instead of trusting mutable human-readable claims. [citation unavailable in inherited source] |
| **Modern SaaS provisioning abuse, SCIM takeover, invite-role inheritance** | Provisioning and invite systems often create or link accounts before the target user proves ownership, or they inherit roles/groups from the provisioning context too early. | The attacker abuses SCIM or invitation APIs to create or link a principal that collides with an existing account or automatically receives workspace roles. Victim interaction may be zero. | Usually **critical** in B2B SaaS because the resulting account often lands directly inside a tenant. A public HackerOne report describes takeover of existing accounts through SCIM provisioning, and public invitation-flow writeups show the same design weakness through team-join paths. [citation unavailable in inherited source] |
| **Cloud gateway and reverse-proxy trust abuse** | Downstream applications trust upstream auth components too absolutely. If the downstream service only verifies a signature but not the correct issuer/signer, or if it is reachable outside the intended proxy path, a malicious upstream can mint apparently valid auth context. | The attacker stands up their own gateway or ALB, gets it to sign a user-claims JWT/header, and presents that upstream-authenticated artifact to a target app that validates cryptography but not provenance. If targets are internet-exposed directly, the blast radius is far worse. | Usually **critical** because it becomes direct auth bypass through infrastructure trust. AWS explicitly states that ALB user-claims JWTs must be signature-verified **and** checked for the expected `signer` value; AWS later issued advisories and updated guidance after the ALBeast class of issues. [citation unavailable in inherited source] |
| **OIDC trust-policy and cloud federation mistakes** | Cloud IAM roles that accept OIDC federation must constrain claims such as `aud` and `sub`; otherwise other tenants, repositories, or workloads under the same issuer may assume the role. | The attacker obtains a valid token from the shared issuer but from the wrong tenant/repository/workload, then targets a weak trust policy that validated the issuer but not the specific subject/audience conditions. | Often **critical** because it becomes cloud-account access rather than just app access. AWS documentation now explicitly discusses OIDC condition keys and examples such as `token.actions.githubusercontent.com:sub`, and cloud-security research highlights vendor-specific trust-policy mistakes as a common failure mode. [citation unavailable in inherited source] |
| **Enterprise device trust abuse and conditional-access trust transfer** | Enterprise ecosystems may trust MFA/device/compliance claims from external organizations or previously issued tokens longer than defenders assume. The danger is stale or transferable trust, not just stolen credentials. | The attacker acquires a valid federated token, registers a new device, abuses trusted external claims, or pivots through OAuth footholds so access is evaluated as “satisfied” even though the attacker’s environment is not truly trusted. | Usually **high to critical** and hard to investigate because telemetry often says the login passed all checks. Microsoft documents that cross-tenant settings can trust MFA and device claims from external Entra orgs; recent OAuth-device-code research shows how token footholds can lead to persistence and device-registration follow-on activity. [citation unavailable in inherited source] |
| **Distributed authentication architecture failures** | In microservice and API-first stacks, identity is often transformed several times: edge login, session service, API gateway, backend token exchange, service account minting, and policy engine lookups. Every transform is a chance to lose audience, issuer, or lifecycle guarantees. | The attacker identifies the weakest hop, then replays or substitutes artifacts downstream. Common targets are internal headers, sidecar/gateway trust, front-end-only checks, and services that treat any JWT with a valid signature as equivalent to a user session. | Severity depends on whether the weak hop reaches privileged APIs; in practice it is often **critical** because the backend is richer than the UI. The ALB guidance, Next.js middleware bypass, and bearer-token leakage cases are all examples of distributed-auth assumptions failing at service boundaries. [citation unavailable in inherited source] |

A representative **cross-tenant SaaS takeover** looks like this. The victim may never knowingly “approve” anything; the bug is the service provider’s account-resolution logic. [citation unavailable in inherited source]

```text
Attacker tenant account --> receives ID token with attacker-controlled email-like claim
                                 |
                                 v
Target SaaS "Login with Microsoft"
                                 |
                     SaaS resolves account by email claim
                                 |
                                 v
Attacker lands in victim account / tenant context
```

The offensive lesson is that **tenant, subject, actor, issuer, audience, and signer are security boundaries, not display metadata**. If any of those become optional in a multi-tenant service, the bug bounty hunter should assume an account-takeover or cloud-access path is nearby.

## Mobile MFA and passwordless attack surface

Mobile and passwordless ecosystems are attractive because they combine three things that bug hunters love: bearer artifacts, local trust, and misaligned UX assumptions. Developers routinely assume the operating system, deep-link routing, biometric prompt, or “magic link” email client will preserve the intended security boundary. In reality, mobile auth falls apart when tokens are exposed to other apps, custom schemes are hijackable, biometric protection gates only the UI and not the action, or recovery fallback is weaker than the primary authenticator. OWASP MAS guidance now explicitly calls out deep-link security and biometric testing, and recent public cases involving Microsoft Authenticator, Shopify’s Android app, and passkey/browser URI handling show that the attack surface is current, not historical. [citation unavailable in inherited source]

| Technique family | Technical explanation and root cause | Exploitation methodology and attacker vs victim workflow | Severity, detection, and representative cases |
|---|---|---|---|
| **Mobile authentication weaknesses, mobile token extraction, deep-link authentication abuse** | Mobile auth often depends on custom schemes, app links, embedded browser callbacks, or app-to-app handoffs. If the callback is not strongly bound to the intended app and channel, another app can receive the auth material. | The attacker installs a malicious app on the same device or abuses a hijackable deep link. The victim follows a legitimate login, but the token or callback is delivered to the wrong app. | Usually **high** on consumer devices and potentially **critical** in enterprise BYOD. OWASP warns deep links can bypass authentication; public cases include intercepted mobile magic links and authenticator/deep-link token exposures. [citation unavailable in inherited source] |
| **MFA bypasses** | MFA frequently fails not because the factor itself is weak, but because it is step-up only in the UI, not on the API; alternate login methods skip it; reset/replacement is weaker than enrollment; or a post-primary-auth state can reach protected endpoints before the second factor is marked complete. | The attacker completes password auth, force-browses to the app, uses alternate SSO/CAS/OAuth paths, races 2FA reset, or phishes a user into completing device-code or consent flows on a legitimate IdP page. | Often **critical** because it invalidates the highest-assurance control in the stack. OWASP explicitly recommends testing incomplete multi-step enforcement and strong MFA reset; public reports show 2FA reset and bypass cases, while live enterprise attacks now abuse OAuth device code to bypass password/MFA capture altogether. [citation unavailable in inherited source] |
| **Magic link abuse and passwordless authentication weaknesses** | Magic links are passwordless, not riskless. Common root causes are token-in-URL leakage, non-single-use links, cross-device routing surprises, email prefetchers, tracker redirects, and treating mailbox possession as high-assurance identity proof. | The attacker intercepts the link via deep link, logs, trackers, or same-device malicious apps; reuses a single-use link that is not actually single-use; or pre-registers / pre-links the victim identity, then waits for the victim to use passwordless auth later. | Typically **high**, occasionally **critical** when the mailbox or device is already partially compromised. Public disclosures include Arrive’s intercepted magic-link flow, reusable magic links, and broader research on weaknesses in email-based passwordless auth. [citation unavailable in inherited source] |
| **Biometric authentication bypasses** | Many mobile apps use biometrics only as a client-side gate to reveal already-present secrets or screens. If the action behind the prompt is reachable by deep link, intent, callback abuse, or weak crypto-object handling, the “biometric protection” is mostly cosmetic. | The attacker triggers the protected action through a path that never invokes the biometric gate correctly, or abuses insecure biometric integration on a rooted/tested device. | Usually **high** because it converts “phone access” or “same-device app access” into account access. OWASP MAS includes dedicated biometric bypass testing, and the Shopify Android report showed fingerprint protection was bypassable through a deep link. [citation unavailable in inherited source] |
| **Phone verification weaknesses and SMS-based takeover risk** | SMS/PSTN is a restricted authenticator because control of the number is weaker and more transferable than developers assume. Even when the channel itself is intact, OTP design bugs often bind the verification to the session instead of the phone/user. | The attacker SIM-swaps, ports the number, or abuses a design flaw in session creation/OTP verification so a valid or predictable artifact works against another identity. | Usually **high** in fintech, gig, ride-share, and consumer onboarding. NIST and OWASP explicitly warn about PSTN risk, and public disclosures show phone/session creation logic enabling future-user account takeover. [citation unavailable in inherited source] |
| **Passkey and platform-authenticator nuances** | Passkeys are far better than passwords, but system-level URI handling, device proximity flows, and weak fallback/recovery can still reintroduce phishable or transferable states. The security property is only as strong as the surrounding browser/OS/channel controls and recovery design. | The attacker abuses browser/OS handling of platform-authenticator intents, or triggers weaker recovery paths because the service treats “lost device” as lower risk than primary login. | Usually **medium to high** operationally, but the impact can still be **critical** per account. Research on CVE-2024-9956 showed passkey phishing through mobile-browser `FIDO:/` intent handling, and later work showed Safari bypassing early mitigations. Recovery guidance consistently warns against weak fallback undermining passkey deployments. [citation unavailable in inherited source] |

A representative **device-code phishing** chain is one of the most important modern enterprise-auth attacks because it bypasses the defender’s intuition. The victim authenticates on the *real* IdP page and may complete MFA successfully; the attacker still receives the token. Microsoft, Proofpoint, CSA, and IC3 all now treat this as an operational threat, not a lab curiosity. [citation unavailable in inherited source]

```text
Attacker -> Device Authorization endpoint: start flow, receive device_code/user_code
Attacker -> Victim: "enter this code to view document / restore access"
Victim  -> Real Microsoft verification URL: enters code, signs in, completes MFA
Attacker -> Token endpoint: polls with device_code
Token endpoint -> Attacker: access token / refresh token
```

A representative **mobile deep-link token theft** path looks like this. This is the same structural issue whether the artifact is a magic link, authenticator callback, or app-to-app login handoff. [citation unavailable in inherited source]

```http
GET /login/magic?token=eyJ... HTTP/1.1
Host: app.link-or-custom-scheme-bridge.example
User-Agent: mobile-email-client
```

If another app or handler receives that URL first, the attacker does not need to beat MFA, biometrics, or passwordless auth directly. They only need to win the **routing race** for the post-authentication artifact.

## Operational testing methodology and defensive lessons

The highest-value offensive workflow is to test authentication as a **distributed state machine** rather than a form. In practice, elite auth testing starts by drawing the full graph: primary login, SSO buttons, mobile flows, deep links, password reset, email/phone verification, 2FA reset, invite links, session refresh, logout, SCIM, OAuth app consent, device code, support/admin impersonation, and cloud trust boundaries. Then the operator tries to break one of seven bindings on every edge: **user binding, tenant binding, issuer binding, audience binding, redirect binding, device binding, and lifecycle binding**. OWASP’s auth/session/MFA guidance and the OAuth/OIDC/SAML research corpus all point in the same direction: attacks happen where one of those bindings is absent or assumed. | Testing order | What to inspect first | Why it is high-yield |
|---|---|---|
| **Map every entrypoint** | Web login, native app login, SSO buttons, mobile deep links, passwordless, reset/recovery, OAuth consent/device code, admin auth, SCIM/invites. | Modern auth flaws often live outside the primary username/password page. [citation unavailable in inherited source] |
| **Capture full state transitions** | Pre-auth cookie → authenticated cookie, password auth → MFA-complete state, reset-start → reset-finish, consent-start → token issue, refresh token → new token family. | Session fixation, skipped MFA, stale-session reuse, and refresh-token races all appear here. [citation unavailable in inherited source] |
| **Validate that the backend enforces auth** | Replay API requests without the browser, delete client-side flags, inject internal headers, test alternate routes. | Front-end and middleware-only auth checks remain a recurring bounty class. [citation unavailable in inherited source] |
| **Abuse identity resolution** | Change email before verification, try social login with matching email, test tenant mix-ups, group/invite merges, SCIM collisions. | Many pre-account takeover and cross-tenant bugs are pure identity-key confusion. [citation unavailable in inherited source] |
| **Stress temporal assumptions** | Parallelize 2FA resets, email verification, refresh redemption, invite redemption, logout/reset followed by replay. | Authentication races are disproportionately common in “single-use” logic. [citation unavailable in inherited source] |
| **Hunt for bearer leakage** | URLs, redirects, browser history, referers, logs, mobile callbacks, `.netrc`, client console snippets, third-party trackers. | Token leakage often bypasses the entire question of auth-factor strength. [citation unavailable in inherited source] |
| **Verify trust provenance downstream** | `iss`, `aud`, `nonce`, `sub`, `tid`, signer ARN, OIDC trust-policy conditions, SCIM source of truth. | Federated auth breaks when downstream consumers validate signature but not provenance. [citation unavailable in inherited source] |

The most realistic modern attack chains are not single bugs; they are **identity trust failures composed across layers**. Four especially operational chains recur in both bug bounty and real incidents:

| Attack chain | Modern exploitation sequence | Why defenders still miss it |
|---|---|---|
| **Pre-account takeover chain** | Unverified email or email-change bug → social-login auto-link or future victim registration → session persists or reset/recovery does not break attacker foothold. [citation unavailable in inherited source] | Teams treat signup, verification, social login, and recovery as separate flows owned by different engineers. |
| **Enterprise consent chain** | Malicious OAuth app or device-code lure → victim authenticates on real Microsoft page and may complete MFA → attacker gets long-lived delegated access → optional refresh-token and new-device persistence. [citation unavailable in inherited source] | Telemetry shows a legitimate login and often a legitimate consent, so incident responders focus on credential theft that never occurred. |
| **Cloud trust chain** | OIDC discovery/DCR SSRF or attacker-controlled upstream signer → cloud metadata or federated artifact obtained → weak AWS OIDC conditions or downstream signer validation → role assumption / backend auth bypass. [citation unavailable in inherited source] | Cloud and app teams each assume the other side fully validated identity provenance. |
| **Session persistence chain** | Token/cookie leak, XSS, magic-link intercept, or same-device app hijack → victim logs out or changes password → old artifact still valid → attacker keeps working. [citation unavailable in inherited source] | The user-facing security action looks successful, so neither the victim nor the SOC immediately recognizes that access persists. |

Defensive teams also tend to systematically underrate three classes of mistake. The first is **trusting mutable identifiers** such as email, `preferred_username`, or display names as stable identity anchors across tenants or providers. The second is **treating upstream auth assertions as complete**, without validating issuer, signer, audience, tenant, or source-specific conditions at the consumer. The third is **assuming strong primary auth compensates for weak lifecycle controls**; in practice, magic links, refresh tokens, logout, reset, recovery, and invitation flows often decide whether an attacker ends up with durable control. Microsoft’s claims-validation guidance, AWS OIDC condition-key guidance, and OAuth/DPoP/refresh-rotation guidance all exist because organizations repeatedly made exactly these assumptions in production. [citation unavailable in inherited source]

The hard practical truth is that **modern authentication security is mostly about preserving context, not just verifying secrets**. Attackers win when a valid event in one context becomes accepted authority in another: the right user in the wrong tenant, the right signature from the wrong signer, the right token at the wrong audience, the right session after the wrong lifecycle event, or the right MFA challenge completed for the wrong principal. The best offensive testers build their methodology around that proposition, and the best defenders engineer every auth edge so that identity cannot survive a context change without being re-proven or cryptographically rebound.
